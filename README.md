# Q2 CoopBot — Go UDP-клиент

Кооперативный напарник для Quake II. Бот входит на обычный сервер Yamagi Quake II как сетевой клиент по протоколу 34. Исполнение, наблюдение мира, маршрутизация и подключение моделей находятся в Go-модуле этого репозитория. Серверу не нужны Gladiator Botlib, мод `game_clean` или специальные команды добавления бота.

## Запуск

Нужны Go 1.23+, выделенный сервер Quake II и легально полученные игровые данные `baseq2`. AAS-файлы в `baseq2/maps` используются Go-маршрутизатором, но игровой сервер их не загружает. Для тестов подготовьте изолированный runtime с **оригинальной** `baseq2/game.dll` Yamagi. Локальные игровые PAK/AAS лежат в `F:\src\quake2\assets\baseq2`; `prepare_runtime.ps1` берёт их оттуда по умолчанию.

```powershell
# После конфигурации отдельной сборки Yamagi:
cmake --build F:\src\quake2\yquake2\build\codex-speed-test --target q2ded game
./scripts/prepare_runtime.ps1
```

`prepare_runtime.ps1` берёт из указанного `AssetsRoot` только PAK/AAS-файлы, копирует сервер и `game.dll` из сборки Yamagi в игнорируемый Git каталог `workspace/runtime/q2go`. Пути источников можно задать через `-AssetsRoot`, `-ServerExe`, `-GameDll`; пригодные AAS из отдельного каталога можно добавить через `-AASRoot`. Файлы из этого каталога должны содержать переходы между областями, иначе скрипт завершится ошибкой.

```powershell
go test ./...
New-Item -ItemType Directory -Force workspace/build/go | Out-Null
go build -o workspace/build/go/q2coopbot.exe ./cmd/q2coopbot
Copy-Item config.example.json config.local.json
./workspace/build/go/q2coopbot.exe --config config.local.json
```

Все настройки Go-клиента находятся в JSON-файле; при запуске нужен только `--config`. Пример — [`config.example.json`](config.example.json). Относительные пути внутри JSON считаются от каталога самого файла, `run.duration` задаётся в формате Go (`30s`, `5m`, `0s` для работы без ограничения). Локальный `config.local.json` исключён из Git. Автоматический тест сохраняет отдельные конфиги обоих клиентов в каталоге результатов. Тестовый RCON-пароль передаётся через `Q2COOPBOT_TEST_RCON` и в JSON не записывается.

Для самостоятельного прохождения задайте `run.mode: "campaign"` и `run.campaign_route: ["base1", "base2", "base3"]`. Маршрут включает стартовую карту и конечную карту: бот выбирает выход к следующей карте и после подтверждённого перехода продолжает новую цель; при достижении последней карты останавливает продвижение. Это заданный маршрут, а не автоматическое открытие всей кампании. `run.next_map` задаёт прежний режим одного перехода и не совмещается с `campaign_route`. Игровые BSP/AAS нужны для каждого проходимого уровня; подробности приёмки и оставшиеся ограничения — [кампания](docs/testing/campaign_return.md).

Для автоматического теста скорости с неподвижным вторым Go-клиентом:

```powershell
./scripts/run_speed_trial.ps1 -GameFrames 100 -SynchronizedStart -UnlimitedLoopbackRate
```

Переключатели `-SynchronizedStart` и `-UnlimitedLoopbackRate` относятся только к отдельной тестовой сборке Yamagi. Без них скрипт может проверить обычный сервер, но не сверяет применённые сервером команды. Подробности: [ускоренные прогоны](docs/testing/q2go_speed_trials.md).

## Запись демо

При заданном `output.trace_jsonl` бот автоматически записывает клиентскую демку рядом с трейсом: `bot.jsonl` → `bot.dm2`. Она воспроизводится в Yamagi от лица бота, с оружием, HUD, звуками и видимыми ему объектами. Паузы бота сохраняются. Старые JSONL нельзя преобразовать в такую демку: нужен новый прогон.

Можно указать отдельный путь или отключить запись:

```json
"output": {
  "trace_jsonl": "artifacts/bot.jsonl",
  "demo_dm2": "artifacts/bot.dm2",
  "record_demo": true
}
```

`record_demo: false` отключает запись. `demo_dm2` работает и без JSONL. Пути считаются от каталога конфига. При смене карты или переподключении создаются `bot-002.dm2`, `bot-003.dm2` и далее; существующие файлы не перезаписываются. Запись начинается с первого полного сетевого кадра после загрузки карты. При штатном завершении файл закрывается маркером конца демо; ошибка записи завершает прогон с сообщением об ошибке.

Для просмотра скопируйте `.dm2` в `baseq2/demos` клиента Yamagi и выполните в игровой консоли:

```text
demomap bot.dm2
```

Клиенту нужны игровые ресурсы соответствующей карты/мода. Файл содержит сетевое наблюдение конкретного бота, а не состояние всех игроков на сервере.

Для просмотра прямо на сайте Run Explorer выберите прогон и переключите «Вид» на «Демо 3D». В той же области появится упрощённый вид от лица бота: BSP без текстур, условные фигуры объектов и HUD, с паузой, перемоткой и скоростью. Записи рядом с JSONL обнаруживаются автоматически. Подробности и ограничения — [веб-проигрыватель](docs/testing/web_demo_playback.md).

В демке скрываются окна inventory/objectives, которые бот открывает для опроса инвентаря; обычный HUD здоровья, брони и патронов сохраняется. Для оконного просмотра 1920×1080 в Yamagi задайте `vid_fullscreen 0`, `r_mode -1`, `r_customwidth 1920`, `r_customheight 1080` перед `demomap`.

## Экспериментальный H-JEPA

Отдельный провайдер `combat_hjepa_v1` сохраняет существующие PPO/BC и режим правил.
Это адаптация [иерархического JEPA](https://h-jepa.com/) к наблюдениям Go-клиента:
три собственных латентных пространства, предсказание на 1/4/16 кадров и выбор
действия через подцели сверху вниз. Обучение выполняется на CUDA; исполнение — в Go.
Используются 845 признаков v6, BC для предложений действий, обратная динамика и
регуляризация дисперсии/ковариации вместо визуального входа и SIGReg оригинала.
Оценка состояния — экспериментальный предиктор здоровья и числа видимых врагов;
скрытие врага тоже меняет этот сигнал, поэтому это не метка победы.

Полный отдельный пилот (нужны подготовленный игровой runtime и Python с CUDA PyTorch):

```powershell
./scripts/run_combat_hjepa_pilot.ps1 -OutputRoot F:/src/quake2/q2coopbot-src/workspace/artifacts/hjepa-new-run
```

Скрипт сохраняет новые демонстрации, отдельные train/validation, веса, checkpoint,
проверку численного совпадения Go/Python и четыре парных игровых проверки с правилами.
Начальный сценарий ограничен `base1`, одним Parasite и Machinegun; автоматического
назначения модели основной нет. Эта первоначальная модель разрешена только в синхронном стенде
с фиксированным оружием и контрактом `legacy_v1`. Выбор оружия и обычная живая
кампания пока не поддержаны этой моделью. Файлы моделей и игровых результатов
остаются в игнорируемом `workspace/artifacts`.

С 16.11.2026 поддерживается отдельная обученная голова выбора оружия:
`weapon_mode=learned_masked_v1`, `weapon_head=combat_masked_weapon_v1`,
`weapon_actor` (845→128→64→12). Маска учитывает наличие оружия, патроны и
свежесть наблюдаемого инвентаря. Необязательный `weapon_sampling_seed` включает
воспроизводимый вероятностный выбор; без него используется максимум вероятности.
Обучение этой головы не меняет motor и модель мира; учитель U1 нужен только офлайн.
Для смешанного оружия используется синхронный стенд с `stock_weapons_fire_v1`
и checked-wall guard. Подробнее: [обучение и native-проверка выбора оружия](docs/testing/hjepa_weapon_selection_20261116.md).

Провайдер также поддерживает поле `planner`: `bc` (без поиска), `flat`
(один уровень), `hierarchy` (первый вариант), `sequence` (поиск последовательностей).
В `sequence` средний уровень проходит четыре шага по 4 кадра до верхней подцели;
нижний проходит четыре шага по 1 кадру до первой средней подцели. Исполняется
только первое действие, после чего планирование повторяется.

Для модели с метками по подтверждённым последствиям сначала экспортируйте
новый набор через `q2hjepa-data`, затем запустите:

```powershell
python scripts/prepare_combat_hjepa_native.py --data train-raw.jsonl --out train-native.jsonl
```

Метки `native_progress_v2` учитывают накопленные урон, убийства, смерти и патроны;
серверные данные используются только как учебные метки. Признаки не меняются.
Файлы `train-native.jsonl` и отдельно подготовленный validation передаются в
`train_combat_hjepa.py`. `audit_combat_hjepa_world.py` проверяет чувствительность
предсказаний к перестановке действий. `run_combat_hjepa_matrix.ps1` сравнивает
замороженные модели на двух экземплярах каждой сцены из проверенного плана
`q2episode`; `report_combat_hjepa_matrix.py` собирает результаты и владение
управлением. PPO с собственным stock-контрактом сравнивается как целая система
с его обязательными ограничителями, поэтому это не чистое сравнение архитектур.

Первый независимый экран `hjepa-diagnosis-v1-20261115` отрицательный:
на 10 боях правила и исходная живая U1 достигли 10 целей, первый H-JEPA — 6,
новые BC/иерархия — 4, поиск последовательностей — 1. Новые версии не продвинуты.
Исторический сценарий первого пилота с Parasite на `base1` не является родным
составом монстров этой карты; новые сборы используют действующий реестр кампании.

Для отдельного обучения предложений действий поддерживается необязательное поле
`motor`: сеть получает все 845 признаков напрямую, а сети модели мира сохраняются.
`train_combat_hjepa_motor.py` обучает её на отдельных кадрах. Для обучения по
проверенным исполненным действиям используйте экспорт `q2hjepa-data` из свежих
эпизодов U1; кадры с вмешательствами ограничителей исключаются из этих меток.
Второй путь — `q2hjepa-teacher`: офлайн-запрос 16 копий замороженной PPO с разными
seed на тех же клиентских наблюдениях. Поле `teacher_action` содержит усреднённую
рекомендацию (для угла используется круговое среднее); поле `action` по-прежнему
содержит реально исполненное действие. Такие рекомендации — отдельные метки BC,
а не доказательство исполнения или данные on-policy PPO. В игре учитель не вызывается.

Отбор меток учителя опирается на подтверждённый native dispatch. Не привязывайте
его к клиентскому кадру `100`: в проверенных записях старт игры на `game_frame=100`
появляется уже в клиентском кадре `98`. Отсечение по номеру клиента теряло первые
два решения каждого боя.

Для обучения модели мира на разнообразных реально выполненных действиях доступны
`q2hjepa-data --guarded-world --terminal-world` и
`prepare_combat_hjepa_native.py --terminal-targets`. Первый режим сохраняет
фактически исполненные команды с ограничителями и переходы со смертью; это отдельные
данные динамики, не экспертные метки и не on-policy PPO. Посмертный инвентарь
маскируется как недоступный только в целевом представлении. Метки `native_progress_v3`
включают оценку следующего состояния, поэтому штраф за смерть не исчезает вместе
с последним живым кадром. Траектории разных моделей с одинаковым seed разделяются
хешем источника. `merge_combat_hjepa_data.py` проверяет объединяемые данные.
Параметр `train_combat_hjepa.py --motor-weights` сохраняет готовую сеть управления
при обучении новых кодировщиков, предикторов и оценок состояния.

Необязательное поле модели `plan_axes` ограничивает компоненты, которые меняет
поиск: `0` — вперёд/назад, `1` — вбок, `2` — поворот, `3` — наклон, `4` — огонь.
Например, `[0,1]` проверяет поиск движения при сохранении прицеливания и стрельбы
обученного motor. При отсутствии поля используется первоначальное пространство поиска.

## Структура

- `cmd/q2coopbot/` — запуск с единственным аргументом `--config`;
- `internal/bot/` — UDP-сессия, планирование и подключение моделей;
- `internal/quake/` — протокол 34, команды движения, BSP и AAS;
- `go.mod` — Go-модуль;
- `scripts/` — запуск и оценка тестовых эпизодов;
- `workspace/tools/bspc/` — отслеживаемые исходники отдельной утилиты подготовки AAS;
- `workspace/build/`, `workspace/runtime/`, `workspace/artifacts/` — локальные сборки, игровые данные и отчёты, исключённые из Git;
- `examples/python-harness/` — прежний Python-прототип и его тесты, сохранённые только как пример;
- `docs/` — текущий [план Go-бота](docs/system2_strategy_tactics_plan.md) и исторические материалы прежней реконструкции.

Для сборки отдельной утилиты AAS с предварительным расчётом переходов:

```powershell
cmake -S . -B workspace/build/aas-current -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build workspace/build/aas-current --target bspc
./scripts/compile_aas.ps1 -BspPath 'F:\path\to\base2.bsp' -OutputRoot workspace/artifacts/aas-base2
./scripts/prepare_runtime.ps1 -AASRoot workspace/artifacts/aas-base2
```

Цель `bspc` собирает Quake II-совместимый форк BSPC: AAS версии 5 содержит области и рассчитанные заранее переходы, которые Go-клиент читает без BotLib. Исходники форка, версия и лицензия GPL-2.0-or-later указаны в [UPSTREAM.md](workspace/tools/bspc/vendor/q2bspc/UPSTREAM.md). Старая неполная реализация сохранена только как отдельная цель `bspc_reconstruction` для исторических тестов. Проверенный запуск и ограничения описаны в [проверке генерации AAS](docs/testing/bspc_reachability.md).

Игровые PAK/AAS-файлы и исполняемый сервер не входят в репозиторий. Исторические документы могут описывать удалённый C-бот; они сохранены для справки и не задают текущую сборку.
