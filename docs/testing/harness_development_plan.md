# План развития Go-харнеса: сценарии, прогоны и анализ

Дата: 2026-09-26. Цель — воспроизводимая студия проверки поведения UDP-напарника. Ядро на Go должно работать без интерфейса; будущий интерфейс использует те же сценарии и отчёты. Python остаётся историческим примером. Артефакты — в игнорируемой `workspace/artifacts/`, конфиги сценариев — в репозитории. Не включать игровые ресурсы и секреты в отчёты.

## Режим повседневной разработки

Основные проверки — ускоренные 2×; 1× оставляем для целевых сравнений и финальной приёмки. Начальный параллелизм — два независимых сервера, на каждом проверяемый бот и сценарный игрок. Каждый эпизод получает свой UDP-порт, runtime, сохранения и артефакты. Исполняемые файлы собираются один раз на пакет; неизменяемые PAK/BSP/AAS могут использовать hard links. Ускорение выше 2× требует отдельной проверки корректности.

Тестовый сервер запускается с `+set ip 127.0.0.1 +set noipx 1`: доступ нужен только локальным клиентам. Значение Yamagi `localhost` по умолчанию открывает IPv4 на всех интерфейсах, что приводило к запросам Windows Firewall для новых путей изолированных серверов. После старта харнес проверяет UDP endpoints по PID: нужный порт должен слушать `127.0.0.1`, нелокальные адреса запрещены. Правила брандмауэра не изменяются. Пакет `scenario-suite-20260926-153936-043` подтвердил 2/2 параллельных прогона при 2× с этой проверкой; отсутствие диалога на экране требует пользовательского наблюдения.

## 1. Сценарии из шагов — первый срез реализован

- Версионированный JSON: карта, начальная постановка, общий игровой кадр начала, последовательность шагов с уникальными ID.
- Первый набор действий: ждать заданное число кадров, идти к точке, тестово переместить актёра. Перемещение явно помечается постановкой теста и не доказывает естественную проходимость.
- Завершать движение по наблюдаемой позиции, проверять таймаут в игровых кадрах. При ошибке останавливаться с причиной и ID шага; не продолжать следующие действия.
- Исполнитель управляет только изолированным сценарным клиентом, не решениями проверяемого бота. Не принимать произвольные консольные команды из JSON.
- Трасса содержит состояние сценария, текущий шаг, начало/конец и причину ошибки. Повторный кадр не повторяет одноразовое действие; смена поколения карты прерывает сценарий.
- Первый связный контроль: два цикла потери игрока и восстановления контакта в одном эпизоде. Приёмка: исполнены все шаги, два наблюдаемых цикла, команды применены без пропусков; отдельно пометить постановку телепортами.

## 2. Единый анализатор на Go — первый срез реализован

- Отделить факты из наблюдений (контакт потерян/восстановлен, смерть, смена карты) от целей планировщика и метрик его действий.
- Проверять целостность трассы и условия постановки до оценки поведения. Различать `fixture_failed`, `trace_invalid`, `behavior_failed`, `passed`.
- Структурированные ожидания: событие произошло в окне, порядок событий, таймаут, отсутствие запрещённого действия.
- Выдавать первый проблемный кадр и короткий контекст; поддержать пересчёт отчёта без сервера. Ошибка метрики не должна выглядеть как ошибка бота.

### Метрики для аналитики

Уже доступны:

- Скорость: реальные секунды, игровые кадры в секунду, фактический коэффициент ускорения; для пакета — длительность исполнения, эпизоды в минуту, минимум/среднее/максимум FPS. Сборка и подготовка runtime исключены из времени исполнения пакета.
- Целостность: пропущенные кадры, ошибки декодирования, отправленные и сопоставленные с сервером команды; поколение карты должно совпадать у обоих клиентов.
- Поведение в окне сценария: число видимых кадров, распределение кадров по целям, кадры с командами движения, количество потерь/возвратов контакта и возобновлений следования.
- Задержки каждого цикла: от потери до возврата контакта и от возврата до первой команды следования. Единица — игровой кадр (0,1 игровой секунды), независимо от ускорения сервера.

Следующие расширения: классификация застревания, дистанция до игрока, смерти/урон/дружественный огонь, задержки дверей и лифтов, CPU/RAM и стоимость подготовки. Затем медиана/p95 на достаточном числе повторов, сравнение с базовым прогоном и пороги регрессии. Отсутствующая метрика должна быть помечена как недоступная, а не нулевая.

Первый срез метрик движения реализован: `actor_motion`/`bot_motion` содержат горизонтальную длину пути по серверным позициям, число интервалов с командой движения, интервалы с перемещением менее одной игровой единицы и максимальную непрерывную серию таких интервалов. Команда кадра N сопоставляется с перемещением N→N+1. Постановочные перемещения актёра исключены; отсутствие позиций даёт `null`. Малое перемещение — диагностический признак, а не автоматический вывод о застревании. `walk_steps` показывает начальную/конечную дистанцию, её сокращение, кадры и подтверждение завершения каждого шага ходьбы. Таймаут актёра сохраняет метрики до отказа и контекст с позициями/командами обоих клиентов.

Не путать команду движения с физическим перемещением. В сценарии с заданным возвращением игрока длительность потери контакта не доказывает эффективность самостоятельного поиска. Не объединять разные карты/сценарии/скорости в одну оценку поведения.

## 3. Инварианты и длинные циклы

Первый срез реализован: `expect.invariants` в сценарии принимает `wait_has_no_movement`, `completed_search_stays_finished`, `visible_contact_clears_search`. Проверки включены в `repeated-contact.json`. Анализатор хранит факт завершения попытки по сущности и кадру последнего наблюдения, даже если последующие строки временно не содержат `search_attempt`; новое наблюдение разрешает новый поиск. Историческое поле `search_attempt.target` не считается действующей целью: проверяется `search_target`, цель планировщика и состояние попытки.

В `report.json` появились `checks` с числом реально проверенных кадров и `problem_context`: проблемный кадр плюс до двух соседних с каждой стороны, шаг сценарного игрока, видимость, цель, команда движения и попытка поиска. Выбирается первое нарушение по времени. Запрошенная проверка без подходящих кадров даёт `invariant_not_exercised`, а не успешный результат. Проверки пока охватывают окно одного поколения карты; смерть/возрождение и смена поколения требуют отдельных сценариев.

- Завершённая попытка не возобновляет старую цель, ожидание не выдаёт движение, свежий контакт сбрасывает бюджет поиска.
- Повторная потеря, смерть/возрождение, смена карты/подключения и сущности не переносят устаревшие цели.
- Добавить последовательности дверей, кнопок и лифтов; затем бой и застревания. Покрывать не только успех, но и недоступную цель, пропажу снимков, таймаут и отказ сценария.

## 4. Повторное исполнение записанных наблюдений

- Запись канонического входа планировщика, версии схемы и необходимых статических данных; детерминированные игровые часы.
- Сравнение решений двух версий на одном входе, первый расходящийся кадр.
- Не считать replay проверкой физики, UDP или будущей траектории после отличающихся команд — это отдельный серверный прогон.

## 5. Наглядный отчёт и интерфейс

- Сначала локальный HTML-отчёт: временная шкала, траектории, цели, переходы, причины отказов и ссылки на исходные трассы.
- Выбор кадра показывает наблюдение, решение и отправленную команду; карта и отображение должны соответствовать сохранённым данным.
- После стабилизации схемы — интерфейс выбора сценария, запуска, истории и сравнения результатов. Не переносить игровую логику в UI.

## 6. Пакеты, сравнения и воспроизводимость

- Идентификатор прогона, сохранённые конфиги, версия кода, контрольные суммы BSP/AAS/сервера; несинхронизированные факторы отмечаются явно.
- Пакеты преимущественно 2×, несколько повторов, отдельные порты/каталоги; 1× — целевой контроль. Первый параллельный пакет реализован через PowerShell с общим Go-анализатором.
- Парные сравнения требуют одинаковых условий и пути сценарного игрока; не объявлять причинный эффект по одному успешному эпизоду.
- Сводка успешности, времени, пути и нестабильных тестов. Финальная проверка поведения — обычная скорость и живой человек.

## Архитектура и переход

### Улучшения, выявленные при естественных проходах

- Реализована проверка маршрутизируемого шага перед первой командой движения: наличие AAS, точное попадание старта/цели в область и существование маршрута. Цель не подменяется ближайшей областью, в том числе для AAS без дерева областей. Проверка выполняется в момент входа в шаг, по фактической позиции актёра; это ещё не предварительный анализ всего сценария до запуска сервера.
- Добавить явные причины остановки сценарного актёра: нет AAS-маршрута, блокировка геометрией, нет опоры, столкновение с другим клиентом. Сейчас различие видно по командам и позициям, но отдельный код причины упростит диагностику.
- Отдельно проверять взаимную блокировку актёра и бота. `scripts/scenarios/blocked-return.json` сохраняет воспроизводитель: обратный маршрут проходит через стоящего бота, актёр получает таймаут. Теперь включён в smoke-пакет как ожидаемый отказ с проверкой причины, шага и кадра. Это проверка диагностики харнеса; она не подтверждает исправление поведения бота.
- Для успешного прохода задавать явные промежуточные точки обхода; не выдавать их за самостоятельное умение бота уступать дорогу. Проверка именно уступания потребует отдельной приёмки бота.
- Сравнивать метрики по ключу сценарий/скорость/версия ресурсов, а не смешивать разные сценарии в одно среднее поведения. Включить сведения о сборке и хешах ресурсов в воспроизводимый манифест пакета.

`internal/harness` — схема, исполнитель шагов и анализ; `internal/bot` — адаптер команд сценарного UDP-клиента; `cmd/` — консольные точки входа. Существующие PowerShell-скрипты временно запускают сервер и процессы. Переносить проверки постепенно, сохраняя прежние сценарии регрессиями. Не начинать с полного переписывания рабочего запуска.

```powershell

Отчёты — `workspace/artifacts/scenario-suite-*/suite-summary.json`, по эпизоду — `report.json`, `result.json`, конфиги, трассы и логи. Анализ можно повторить без сервера через `go run ./cmd/q2scenario-report --config <report-config.json>`.

### Ожидаемые отказы

В `expect.failure` задаются `reason`, `step_id`, `min_frame`, `max_frame`. Поддержаны `step_timeout` для шага с таймаутом и отказы маршрутизируемого `walk`: `aas_unavailable`, `route_target_outside_aas`, `route_start_outside_aas`, `route_unavailable`. В отчёте сохраняются фактические `state: fixture_failed`, причина, `failed_step` и кадр. Независимые поля `accepted` и `expectation` показывают, совпал ли результат с ожиданием. CLI возвращает успех только при `accepted: true`; пакет отдельно считает `expected_failures` внутри общего числа принятых тестов.

Повреждённая или неполная трасса, другое поколение карты, другая причина/шаг/кадр, нарушение заданного инварианта и неожиданное успешное прохождение не принимаются как ожидаемый отказ. Инварианты проверяются и на префиксе неудачного эпизода. Ожидания числа циклов контакта пока не смешиваются с ожидаемым отказом; это явно отклоняется валидатором.

Приёмка 2026-09-26: `scenario-suite-20260926-135430-231` — 6/6 принятых тестов на 2× с параллелизмом 2: четыре нормальных завершения и два подтверждённых ожидаемых таймаута `walk-back` на кадре 104. Go-тесты проверяют все перечисленные варианты несовпадения. Плановое улучшение: для отказов динамической блокировки добавить проверяемые признаки препятствия, чтобы совпадение таймаута не ошибочно считалось доказательством конкретной причины столкновения.

### Проверка маршрута и причины остановки

В `scenario.movement_reason` и контекст ошибки добавлены причины временной остановки: `not_grounded`, `geometry_unavailable`, `within_horizontal_tolerance`, `static_hull_blocked`, `no_ground_support`. Эти состояния не завершают сценарий немедленно, поскольку могут измениться; сохраняется игровой таймаут. Терминальные ошибки AAS/маршрута останавливают шаг до выдачи движения и не допускают следующих шагов. Проверка маршрута не подтверждает отсутствие динамических препятствий или доступность дверей.

Сценарий `invalid-route-target.json` вошёл в smoke-пакет: цель на границе пола вне AAS должна отклоняться на кадре 44. Пакет `scenario-suite-20260926-135811-596` принял 8/8 тестов: четыре нормальных завершения и четыре ожидаемых отказа. После строгой проверки областей финальный пакет `scenario-suite-20260926-135939-260` подтвердил все четыре сценария по одному повтору на 2×, параллелизм 2. Go-тестами проверены причины отказа, невозможность продолжения после него и отсутствие подстановки ближайшей области.

### Досрочное завершение

Реализован явный параметр пакета `tail_frames`: `0`/отсутствие оставляет полный лимит, `2..1000` включает досрочное завершение. Smoke использует 5. После терминального состояния актёр атомарно публикует карту, поколение, состояние и кадр результата в отдельный файл эпизода. Проверяемый клиент доигрывает хвост и ждёт следующий серверный снимок, подтверждающий последнюю команду. Затем штатный оркестратор завершает актёра и сервер. Поколение карты и последняя строка трассы сверяются с сигналом, проверка всех применённых команд сохраняется. Старый файл в каталоге прогона отклоняется. Это подтверждающий хвост; семантическое окно анализатора по-прежнему заканчивается терминальным кадром сценария. Нужное позднее поведение должно быть явным шагом `wait` до завершения.

Приёмка: `scenario-suite-20260926-140531-911` — 8/8 принятых тестов с ранним выходом. В сравнении с полным пакетом `scenario-suite-20260926-135811-596` время исполнения сократилось с 62,69 до 35,66 с (43,1% в одной паре измерений, без сборки/подготовки). Все отправленные команды сопоставлены с сервером. Семь наборов метрик совпали полностью; в одном повторе поиска изменились длина пути и распределение команд/целей, но все кадры потери/возврата контакта и инварианты совпали. Поэтому это не доказательство побитной детерминированности. Финальная проверка дополнительных сверок трассы — `scenario-suite-20260926-140647-183`, 4/4. Go-тесты проверяют ожидание хвоста и подтверждения команды, отказ при чужом поколении, однократную публикацию только терминального результата.

Дополнение к воспроизводимости: фиксировать seed сервера и начальное динамическое состояние и сравнивать префиксы трасс до терминального кадра. Это позволит отделить случайность мира от влияния запуска и ускорения. Не обещать одинаковую траекторию только по совпадению JSON сценария.

### Манифест входных данных

Реализован `manifest.json` для каждого пакета: Git revision и признак незакоммиченных изменений, версии Go/PowerShell, SHA-256 исходников Go и запускающих скриптов, сохранённых конфигов сценариев, фактических клиентских бинарников, серверов, game.dll, PAK/BSP/AAS всех изолированных runtime. Манифест не сохраняет содержимое игровых ресурсов, переменные окружения или секреты. Хеши исходников вычисляются до сборки, файлов прогона — перед стартом; обе группы повторно проверяются после исполнения. Изменение входных данных даёт `provenance_valid: false` и ненулевой выход пакета независимо от успеха сценариев. Это защита от случайных изменений, а не криптографическая подпись отчёта.

`preparation_seconds` и `verification_seconds` показывают цену сборки, подготовки и контроля хешей отдельно от `execution_wall_seconds`. `fixture_fingerprint` в результате эпизода связывает сценарий, ресурсы runtime, timescale и tail_frames без зависимости от порта/каталога/номера повтора. Версии проверяемого клиента и анализатора остаются отдельными хешами манифеста: совпадение условий допускает сравнение разных реализаций, но не означает их идентичность.

Seed пока явно `null`, `deterministic_world_verified: false`: манифест доказывает идентичность файлов, а не динамического состояния мира. Незакоммиченные исходники учитываются по хешам, но не архивируются; хеш не позволяет восстановить утраченное содержимое. Следующее улучшение — сравнение двух манифестов с перечислением отличий и запретом выдавать несовместимые наборы условий за парный эксперимент.

Первая приёмка: `scenario-suite-20260926-141037-235` — 4/4, контроль исходников и 183 файлов прогона пройден. `scripts/test_harness_manifest.ps1` проверяет изменение содержимого, независимость отпечатка от порядка записей и отклонение пути вне корня.

Финальная приёмка отпечатков условий: `scenario-suite-20260926-141153-026` — 8/8, `provenance_valid: true`; получены четыре разные группы сценариев ровно по два повтора, несмотря на разные порты и каталоги. Подготовка заняла 10,32 с, итоговая проверка хешей 3,41 с — эти затраты теперь видны отдельно. Возможное улучшение после замеров: проверять общий неизменяемый набор ресурсов один раз при доказанной идентичности hard links, сохраняя полный контроль копируемых файлов; не кешировать хеш только по имени/mtime.

### Сравнение пакетов

Реализована команда `go run ./cmd/q2suite-compare --config <comparison.json>`. Конфиг содержит `baseline`, `candidate`, `output`; относительные пути разрешаются относительно конфига. Команда читает сводки и манифесты, требует подтверждённую неизменность входов и одинаковый хеш анализатора. Сценарии сопоставляются по `fixture_fingerprint`, независимо от числа повторов. Разные наборы условий выводятся отдельными несовпавшими группами; пакет в целом получает `compatible: false` и ненулевой код выхода. Результаты сохраняются и при несовместимости.

Для совместимых групп показаны число принятых тестов, count/mean/min/max числовых скалярных метрик и разница средних. Отсутствующие метрики — `null`, без выдуманного нуля; число наблюдений доступно для каждой метрики. Массивы событий/задержек пока не агрегируются. Перечислены изменившиеся исходные файлы и изменение клиентского бинарника. Изменение клиента допускается для сравнения версий; изменение анализатора требует пересчёта обоих отчётов одной версией. `compatible` характеризует условия сравнения, а не успех сценариев и не отсутствие регрессии. Проверка опирается на записанный манифест, не является повторной криптографической проверкой всего каталога при чтении.

Приёмка: свежий пакет `scenario-suite-20260926-141545-196` — 4/4 с манифестом; сравнение с `scenario-suite-20260926-141153-026` — четыре совместимые группы (два повтора против одного). Результат `workspace/artifacts/suite-comparison.json`. Go-тесты покрывают несовместимые анализаторы/условия, неподтверждённое происхождение, отсутствующие метрики, разброс повторов и изменение клиентской реализации. Статистическая значимость, пороги регрессии и поиск первого различающегося кадра остаются следующими улучшениями анализа.

### Диагностика движения и наблюдаемых препятствий

`metrics.actor_diagnostics` содержит причины остановки контроллера (`controller_hold_frames`) и интервалы фактического отсутствия движения (`stalls`). Серия диагностируется после трёх последовательных интервалов: обычный шаг `walk`, ненулевая команда движения в предыдущем кадре, подтверждённая опора на землю в обоих снимках и смещение в 3D менее одной единицы. Пропуски/смена поколения, другая задача, движение, отсутствие позиций/grounded или отсутствие команды разрывают серию. Выводятся первый кадр команды, кадр обнаружения, последний снимок и длина серии.

Для каждой серии сохраняются только текущие наблюдения напарника/врагов в пределах 64 единиц по горизонтали и 48 по высоте: вид, доступный ID врага, число наблюдавшихся интервалов и минимальное расстояние. Отсутствующие сущности не восстанавливаются из памяти. Это корреляция, не доказательство физического столкновения: точный blocker ID требует серверной телеметрии collision trace; BSP movers пока не классифицируются.

В `expect.failure` добавлены `min_stall_frames` (от 3) и необязательный `nearby_kind` (`teammate`/`enemy`). Свидетельства должны относиться к неудачному шагу и покрывать требуемое число интервалов; неподходящая/пропущенная телеметрия не принимается. `blocked-return.json` теперь требует минимум 10 интервалов и наблюдение напарника рядом, а не только таймаут на кадре 104.

Первая проверка `scenario-suite-20260926-141917-645` — 4/4: обратный проход имеет 39 интервалов без продвижения и наблюдаемого напарника на расстоянии 32,13; обычный проход и ошибка AAS такой серии не имеют. Go-тесты покрывают отсутствие команды/grounded, реальное движение, пропуски, неподходящую высоту препятствия и условия принятия ожидаемого отказа.

Финальный пакет с усиленным ожиданием `scenario-suite-20260926-142035-771` — 8/8, манифест входов подтверждён. Оба повтора блокировки приняты с требуемыми свидетельствами; семантика успешных сценариев сохранена.

### Смерть и возрождение сценарного игрока

Добавлен типизированный шаг `respawn_cycle` с игровым таймаутом. Исполнитель однократно отправляет `kill`, ждёт здоровье ≤0, затем посылает импульсы кнопки атаки для возрождения и завершает шаг только после наблюдаемого здоровья >0. Повторный кадр не повторяет команду смерти; новый цикл сбрасывает сведения о предыдущем. Неожиданная смерть вне этого шага остаётся ошибкой `actor_dead`. Неподтверждённая смерть/возрождение заканчивается таймаутом, не автоматическим успехом.

Трасса шага содержит `death_frame`/`respawn_frame`, метрики — `actor_lifecycle`. Анализатор независимо требует события «жив → мёртв → жив» внутри каждого завершённого шага: одного статуса исполнителя недостаточно. Недоступное здоровье не считается нулём. Интервалы цикла исключаются из ходовой длины пути актёра (`excluded_respawn_intervals`), чтобы перемещение при респауне не выглядело пройденным маршрутом.

`respawn-cycle.json` проверяет два цикла с паузами после появления игрока. Приёмка `scenario-suite-20260926-142420-281`: 10/10 на двух параллельных серверах при 2×, манифест подтверждён. В обоих повторах смерти на кадрах 72/140, возрождения 82/150; 147/147 команд бота сопоставлены с сервером. Go-тесты проверяют однократную команду, необходимость смерти перед возрождением, сброс между циклами и независимое подтверждение анализатором.

Граница этой приёмки: цикл сценарного игрока, не собственная смерть бота и не правильность его реакции на мёртвого напарника. Следующие проверки должны отдельно требовать сброса старой цели, безопасных команд, повторного сопровождения после возрождения и отказа от старой идентичности при замене сущности.

### Реакция на возвращение напарника

Трасса проверяемого бота теперь сохраняет `teammate_entity`. `metrics.companion_lifecycle` сопоставляет ID актёра с выбранным ботом напарником, отмечает кадры смерти/респауна, первого повторного наблюдения и возобновления команды следования. Неизвестный или другой ID не подтверждает восстановление. Здоровье берётся только из трассы актёра для анализа; оно не передаётся в решения бота.

Инвариант `respawned_actor_followed` требует подтверждённого следования после каждого наблюдённого цикла. Сценарий после каждого респауна явно возвращает живого актёра в видимую точку через `place`, затем проверяет два восстановления контакта и сброс поиска. Это постановочная проверка восстановления поведения; она не доказывает самостоятельный путь игрока от места респауна.

Выявленное ограничение записывается метрикой `dead_actor_tracked_frames`: в исходной трассе тело продолжает попадать в `teammate` до респауна. Это не считается подтверждением корректной реакции на смерть. В план развития бота требуется отдельный пункт: определить доступные по UDP признаки смерти игрока, отличать тело от живого напарника и проверять сброс старой цели без использования привилегированного здоровья из харнеса.

Приёмка: первый пакет `scenario-suite-20260926-142941-503` выявил слишком близкую вторую точку возврата — бот выбирал прикрытие, поэтому обязательное движение не подтверждалось. Точка вынесена дальше без ослабления проверки. Целевой пакет `scenario-suite-20260926-143125-932` — 2/2; в обоих повторах наблюдение и команда следования восстановлены на кадрах 84 и 154, проверены оба цикла отдельно и совпадение ID. Метрика тела — по 10 кадров в каждом цикле; это открытая задача поведения бота. Go-тесты исключают подмену другим/неизвестным игроком и принятие одной реакции за два восстановления.

Полная студия, интерфейс, replay, гарантированная очистка дочерних процессов при принудительном завершении оркестратора и пакетный Go-оркестратор пока не реализованы. Следующий срез — смена карты и поколений в сценариях, затем replay и наглядный отчёт. Исправление распознавания мёртвого напарника остаётся отдельным пунктом поведения бота.

### Идентичность кадров при смене карты

Отчёт содержит `session_timeline.actor/bot`: последовательность сегментов всех записанных кадров, включая подготовку и подтверждающий хвост. Каждый сегмент хранит первую/последнюю позицию в JSONL (нумерация с 1), карту, поколение, локальный кадр и число строк. Повторная загрузка той же карты создаёт отдельный сегмент. Диагностика отмечает дубликаты, обратный ход и пропуски кадров, смену карты без нового поколения и возврат к ранее записанному поколению. Начало нового поколения не требует кадра 0: первая доступная UDP-трасса может начинаться позже.

Проблемы вне сценарного окна пока являются диагностикой, не дополнительным критерием приёмки. Внутри окна по-прежнему нужна непрерывность; вставку другой карты между подходящими кадрами больше нельзя незаметно отбросить фильтром. При неожиданной смене поколения исполнитель по-прежнему останавливается, анализатор сохраняет `map_generation_changed`, классифицирует трассу как `trace_invalid` и записывает `problem_location` с поколением и строкой. Сброс номера кадра больше не превращает этот отказ в `scenario_incomplete`.

Это основа анализа нескольких карт, не реализованный шаг перехода. Следующая реализация должна включать явный разрешённый переход, отдельный бюджет ожидания, привязку шагов и терминального результата к поколению, сверку последовательности карт двух клиентов и локальные окна метрик по сегментам. Нельзя просто разрешить разрывы в существующем однокартовом анализаторе. Перезапуск/переподключение с новой сессией также требует идентификатора сессии: одного `spawncount` недостаточно при перезапуске сервера.

Сверка последовательности реализована отдельным ожиданием `expect.map_sequence`: от 2 до 16 имён карт, последнее совпадает с картой основных шагов. Анализатор требует точного числа и порядка сегментов у обоих клиентов, одинаковых поколений соответствующих сегментов и хотя бы одного общего кадра в каждом. Поколения непрозрачны: численно меньшее новое значение допустимо. Повтор одной карты требует нового поколения. Для этой явно включённой проверки разрывы всей записанной сессии, включая подготовку и хвост, становятся отказом приёмки. Ожидаемый таймаут шага не может скрыть нарушение последовательности карт.

`repeated-contact.json` требует `base1 → base2`, реально выполняемый существующим оркестратором при подготовке. Это проверка перехода и последующего сценария на конечной карте; команда перехода в произвольном шаге пока не реализована. Без `map_sequence` прежняя семантика окна сохраняется. Первая запись каждого клиента может различаться по кадру; синхронный старт трасс не требуется, но полное отсутствие совместного наблюдения поколения отклоняется.

Приёмка последовательности: `scenario-suite-20260926-154247-479` — 10/10, включая четыре ожидаемых отказа; 2×, два параллельных сервера, 49,13 с исполнения и подтверждённый манифест. Два повтора `repeated-contact` приняты с обязательной проверкой перехода у обоих клиентов. `go test ./...` прошёл; Go-тесты отклоняют пропущенную/лишнюю карту, чужое поколение, непересекающиеся окна, разрыв и повтор карты без нового поколения, а также нарушение последовательности при ожидаемом отказе шага.

### Исполнитель многокартовой сессии — ядро и первый UDP-прогон

В `internal/harness/session.go` добавлены строгая схема `Session` и `SessionRunner`. Сессия содержит 2..16 этапов с уникальными ID; каждый этап включает отдельный существующий `Scenario`, его локальный бюджет кадров и ожидания поведения. `transition_timeout_ms` — отдельный реальный таймаут загрузки (100..120000 мс); игровые шаги сохраняют кадровые таймауты. Определения этапов пока требуют нормального завершения, без `expect.failure` и отдельного `map_sequence`: порядок карт определяется самой сессией.

Исполнитель выдаёт однократное намерение `ChangeMap` после завершения шагов этапа. До нового поколения остаётся в `waiting_map`; повтор снимка не повторяет команду. Правильная карта в новом поколении создаёт новый исполнитель шагов. Повтор той же карты допустим только с новым поколением. Другое имя карты, повтор уже использованного поколения, неожиданный переход во время подготовки/выполнения этапа, запоздалый старт, ошибка маршрута или шага останавливают сессию. Состояние сохраняет ID этапа, его исходный статус и полную идентичность последнего снимка.

Контракт адаптера: записать последний снимок завершённого этапа до отправки команды смены карты; обслуживать монотонный реальный watchdog также во время загрузки; обеспечить внешний watchdog начального подключения; применить новую постановку актёра/бота до `start_frame` следующего этапа. `ChangeMap` является намерением, а не подтверждением перехода. Клиент подключён через `test.session` и `test.session_role: actor/observer`; актёр требует idle и тестовый RCON, наблюдатель выполняет политику бота. Роли заново расставляются при новом поколении; промежуточный завершённый этап не публикует окончание всей сессии.

Проверка ядра: `go test ./...` прошёл. Покрыты два этапа с локальным сбросом кадров и численно меньшим новым поколением, перезагрузка той же карты, таймаут без новых снимков и на точной границе, чужая карта, изменение поколения до старта, возврат старого поколения на третьем этапе, ошибка маршрута/смерть и запрет дальнейших действий. Живая UDP-приёмка этого исполнителя остаётся открытой.

Реализован отдельный запуск `./scripts/run_session_trial.ps1 -Config scripts/scenarios/session-trial.json`: изолированный runtime, loopback, сервер и два клиента, финальный хвост наблюдателя и автоматический анализ. `q2scenario-report` принимает `session` вместо `scenario`; проверяет порядок/поколения карт и идентичность этапов, затем анализирует каждое поколение отдельно. Параллельный пакет, манифест и сравнение сессий пока не подключены; отдельный запуск также ещё не переносит полную сверку отправленных команд с серверным журналом из `run_speed_trial.ps1`. ### Барьер готовности этапа — реализован

`readiness_barrier: true` в сессии включает подтверждение обеих ролей после каждой загрузки. Клиент записывает готовность только после наблюдённой расстановки: живой игрок, контакт с землёй, XY не дальше 16 единиц от цели и разница высоты не более 32 (учитывает падение из точки постановки на пол). Пока нет двух подтверждений, оба клиента отправляют нулевые команды. Подтверждения атомарно сохраняются в отдельном каталоге рядом с `scenario_result`, с картой, поколением, индексом этапа, ролью и кадром. Старая запись своей роли отклоняется; нужен свежий каталог прогона.

Общий старт — максимум двух кадров готовности плюс 10 кадров на обмен. Он записывается в трассы обоих клиентов как `session_start_frame`; локальный бюджет шагов переносится целиком, без изменения длительности шагов. Если клиент пропустил выбранный старт, прогон отклоняется. Ожидание готовности ограничено `transition_timeout_ms`. Это барьер действий клиентов; серверный мир во время подготовки продолжает симуляцию, поэтому он не обеспечивает одинаковое состояние монстров между запусками.

Анализатор использует фактический старт каждого этапа, требует согласия обеих трасс и запрещает команды движения/стрельбы до старта. `two-map-session.json` больше не использует запас до кадра 100. Финальный прогон `session-trial-20260926-160658-786` принят на 2×: на `base1` роли готовы на кадрах 32/38, старт 48; на `base2` — 39/78, старт 88. `go test ./...` прошёл; дополнительные тесты проверяют чужую карту/поколение/роль, перенос бюджета, пропущенный старт и команды до барьера.

Остаётся включить многокартовые сессии в параллельный пакет, манифест и сравнение, перенести полную сверку команд с серверным журналом. Следующая синхронизация мира при фиксированном seed — отдельная задача воспроизводимости, не свойство текущего барьера.

### Сверка команд и остановка перед переходом — реализованы

Многокартовый отчёт теперь требует `server_log` в конфиге `q2scenario-report`. Go-анализатор читает `sv_test_applied_cmd`, проверяет диапазоны полей и сравнивает все поля команд наблюдающего бота по паре поколение/номер сетевой команды. Охватывается вся трасса, включая подготовку и хвост. Пропущенные, лишние и дублированные `new`-команды, несовпадение значений, отсутствие номера и повреждённые строки отклоняют прогон. Повторные команды восстановления сети (`old`, `oldest`, `last`) считаются отдельно и не заменяют доказательство применения `new`. Это проверка команд наблюдателя; журнал сервера пока не доказывает команды сценарного актёра.

Повторный анализ `session-trial-20260926-160658-786` выявил потерю последней команды первой карты: 49 из 50. Согласование перехода исправлено: актёр публикует запрос только после записи терминального кадра; наблюдатель доходит как минимум до этого кадра, прекращает отправку и ждёт следующего снимка, подтверждающего последнюю команду. Актёр также ждёт подтверждения своей последней команды и готовности наблюдателя. После запроса перехода оба потока остаются остановленными до нового поколения. Внешний watchdog и таймаут перехода сохраняются.

Приёмка: `session-trial-20260926-161205-205` — 88/88 команд; финальный `session-trial-20260926-161348-039` — 50/50, ноль команд восстановления, обе карты и этапы приняты на 2×. Разное число кадров подготовки между запусками не является детерминированностью мира. `go test ./...` прошёл; тесты проверяют дубликаты, пропуск/подмену команды, одинаковые номера в разных поколениях, повреждённый журнал и необходимость подтверждения обоих потоков перед переходом. Следующий пункт — включить сессии в параллельный пакет с манифестом и сравнением результатов.

### Многокартовые сессии в общем пакете — реализованы

`run_scenario_suite.ps1` принимает массив `sessions` наряду со `scenarios`; допускается смешанный пакет. Сборка клиента и анализатора выполняется один раз, каждый прогон использует свой runtime/порт и ограниченный общий параллелизм. Для сессий обязателен `tail_frames` от 2 до 1000. Подготовленный конфиг запуска сессии входит в манифест вместе с её определением, бинарниками и ресурсами; проверка неизменности до/после исполнения сохраняется. `fixture_fingerprint` дополнительно различает тип session, а пути, порты и номер повтора не мешают сравнению одинаковых условий.

В сводке сессии сохраняются метрики этапов под `metrics.phases.phase_0`, `phase_1` и т.д., доказательство применения команд и `speed.orchestration_wall_seconds`. Это время запуска/исполнения/анализа сессии; оно не выдаётся за FPS игровой симуляции. Общая сводка FPS использует только прогоны с реально вычисленным `game_fps`. `q2suite-compare` сравнивает вложенные скалярные метрики этапов без объединения разных карт в одно среднее.

Запуск контрольного смешанного пакета: `./scripts/run_scenario_suite.ps1 -Config scripts/scenarios/harness-session-suite.json`. Приёмка `scenario-suite-20260926-161800-951` — 4/4 на двух серверах при 2×, 20,39 с исполнения; обе сессии подтвердили по 49/49 команд. Второй пакет `scenario-suite-20260926-161845-492` — 2/2. Манифесты подтверждены, сравнение `workspace/artifacts/session-suite-comparison.json` совместимо по двум группам (обычный сценарий и сессия), метрики обоих этапов доступны отдельно. Первый неудачный пакет `scenario-suite-20260926-161659-662` выявил ошибку разрешения абсолютного пути prepared runtime; исправлено до итоговой приёмки.

Следующие незакрытые блоки: переподключение/сброс устаревшего состояния и собственная смерть бота, расширенные взаимодействия, воспроизводимость мира, replay, наглядный отчёт и интерфейс, аварийная очистка процессов и перенос оркестрации в Go. Пакетные сессии не закрывают эти требования.

### Сброс поиска на границе поколений — первая поведенческая проверка

Сессия поддерживает `invariants: ["search_reset_on_transition"]`. Анализатор требует хотя бы одну границу, перед которой в последней записанной команде поколения активен поиск (`search_last_seen`/`probe_last_seen` или `search_target`). В первом записанном решении следующего поколения не должно быть поисковой цели, поискового режима или старой попытки `search_attempt`. В отчёте `transition_checks` сохраняются обе карты, поколения, кадры и цели. Если поиск не был активен перед границей, проверка считается невыполненной и прогон не принимается. Новому поиску позднее в поколении эта проверка не препятствует.

Контроль: `./scripts/run_scenario_suite.ps1 -Config scripts/scenarios/search-reset-suite.json`. `search-reset-session.json` выполняет `base1 → base2 → base1`; на `base2` актёр уходит из видимости перед переходом. Пакет `scenario-suite-20260926-162235-172` — 2/2 на двух серверах при 2×, манифест подтверждён. В обоих случаях перед переходом наблюдался `probe_last_seen`, после него — `wait_for_teammate`; сервер подтвердил 118/118 и 154/154 команд. Go-тесты проверяют отсутствие условий, оставшийся target/attempt/режим и допустимость нового поиска позднее.

Граница приёмки: это проверка поискового состояния в первом записанном решении после перехода. Она не доказывает сброс всех подсистем бота, корректность нового подключения к тому же серверу, собственный респаун бота или отсутствие ошибки между незаписанными снимками. Эти сценарии остаются открытыми.

### Управляемая смерть и возрождение наблюдающего бота

В этапе сессии доступен `observer_respawn_cycle` с `after_frames`, `timeout_frames`, `recovery_frames`; требуется барьер готовности. Отсчёт идёт от согласованного старта этапа. Харнес один раз посылает `kill` живому наблюдателю и при наблюдаемой смерти чередует кнопку respawn/отпускание, пока не увидит положительное здоровье. Это явно тестовое воздействие: трасса содержит `test_observer_kill` и `test_observer_respawn`, отчёт — `stimulus: scripted_kill_and_respawn`. Обычная политика бота по-прежнему не получила автоматическое возрождение.

Анализатор требует единственный kill в заданном кадре, живое состояние при воздействии, наблюдённую смерть и последующее возрождение в срок, отсутствие команд движения при смерти и заданное число живых кадров после возрождения. Отсутствующее здоровье, неполный цикл, новая смерть и непомеченные команды respawn отклоняются. Метрика пути исключает интервалы, один из концов которых относится к мёртвому игроку (`excluded_dead_intervals`), включая скачок позиции на респауне.

Запуск: `./scripts/run_scenario_suite.ps1 -Config scripts/scenarios/observer-respawn-suite.json`. Финальный пакет `scenario-suite-20260926-162858-090` — 2/2 на двух серверах при 2×, манифест подтверждён. В `run-000`: смерть на кадре 105, возрождение 115, пять проверенных живых кадров; 189/189 команд наблюдателя применены сервером. Go-тесты проверяют однократное воздействие, импульсы respawn, неполные/повреждённые циклы и исключение скачка из длины пути.

Эта проверка подтверждает обработку принудительного цикла жизни в харнесе и продолжение наблюдений. Самостоятельный respawn политики, сброс всех её целей после собственной смерти и возобновление сопровождения после естественного возвращения к игроку остаются отдельными проверками. Переподключение без смены карты также ещё не реализовано.

### Управляемое переподключение к той же карте — реализовано

Этап может задавать `entry: reconnect`; его карта должна совпадать с предыдущей. После подтверждения последних команд оба клиента согласованно закрывают UDP-соединения, проходят новый handshake, снова расставляются и ожидают барьер готовности. Это намеренное переподключение обеих ролей в работающий сервер, а не имитация внезапного сетевого обрыва или перезапуска сервера.

Трасса содержит `connection`: номер успешно принятого соединения в жизни процесса. Повтор `client_connect` не увеличивает его; поколения карт остаются отдельной сущностью. Отчёт разделяет этапы по поколению и подключению, требует для reconnect прежнее поколение и новый номер соединения у обоих клиентов. Для обычного перехода всё ещё обязательно новое поколение. Обратный ход кадров внутри прежнего поколения при новом соединении отклоняется.

Сверка команд для новых трасс использует тройку подключение/поколение/номер пакета. Серверное подключение определяется строкой успешного подключения трассируемого клиента `GoCoopMate`, а не повторами handshake. Поле `connection_identity_verified` сообщает, выполнена ли эта дополнительная сверка. Старые трассы без `connection` читаются по прежнему ключу поколение/пакет и не получают нового доказательства; смесь известных и отсутствующих идентификаторов отклоняется.

Приёмка: `scenario-suite-20260926-163638-456` — 2/2 на двух серверах при 2×; `run-000` сохранил `base1` и поколение 1232907478, сменил подключение 1 → 2, подтвердил 53/53 команды. Запуск: `./scripts/run_scenario_suite.ps1 -Config scripts/scenarios/reconnect-suite.json`. Первый пакет выявил кратковременный Windows sharing violation при чтении атомарного сигнала; только ошибки sharing/lock теперь ожидаются повторно в пределах действующего watchdog. Повреждённый JSON и неверная идентичность не маскируются.

Go-тесты проверяют повтор ответа подключения, повтор handshake в серверном журнале, одинаковые номера команд разных соединений, необходимость смены соединения при неизменной карте и запрет принимать reconnect за новую карту. Сценарий пока проверяет reconnect и выполнение шагов ожидания; сброс активной поисковой задачи при reconnect, внезапный обрыв одного клиента и восстановление после рестарта сервера остаются отдельными проверками.

Итоговая смешанная регрессия `scenario-suite-20260926-163943-009` — 3/3: обычный сценарий, переход карты и reconnect. Предыдущая `scenario-suite-20260926-163757-404` — 2/3: обнаружено, что `os.IsNotExist` не распознаёт составную ошибку повторного чтения; проверка исправлена на `errors.Is`. Windows-тест открывает настоящий файл без разрешения совместного чтения и подтверждает, что барьер остаётся в ожидании. `go test ./...` прошёл.

### Сброс активного поиска при переподключении — проверен

Добавлен инвариант `search_reset_on_reconnect`: при прежнем поколении карты и новом номере соединения первый записанный ответ бота не должен содержать прежнюю поисковую цель, режим поиска или `search_attempt`. Перед границей поиск должен быть активен; иначе проверка считается невыполненной. Смена поколения не может заменить эту проверку. Если запрошены несколько инвариантов, каждый должен быть реально задействован.

Сценарий `reconnect-search-session.json` переводит клиентов с `base1` на `base2`, скрывает актёра до начала поиска, затем переподключает обе роли к той же карте. Запуск: `./scripts/run_scenario_suite.ps1 -Config scripts/scenarios/reconnect-search-suite.json`. Приёмка `scenario-suite-20260926-164247-860` — 2/2, ускорение 2×, два параллельных сервера, 15,10 с исполнения, `provenance_valid: true`. В обоих прогонах перед reconnect наблюдался `probe_last_seen`, после него — `wait_for_teammate`; поколение сохранено, подключение изменилось 2 → 3. `go test ./...` прошёл.

Это подтверждает сброс поискового состояния при управляемом переподключении в первом записанном решении. Внезапная потеря связи одного клиента, перезапуск сервера и сброс прочих подсистем остаются открытыми. Следующие работы по харнесу: корректная классификация поведенческих отказов сессии в сводке пакета, сценарии сетевого восстановления, replay и наглядный отчёт.

### Потеря связи одного клиента — транспорт для постановки

Добавлен внешний Go UDP-прокси `cmd/q2netfault` / `internal/harness/netfault`: ограниченный по времени обрыв в обе стороны, закреплённый клиент, только loopback, журнал передач/потерь без содержимого пакетов. Конфиг и границы доказательства описаны в [network_faults.md](network_faults.md).

Go-тесты с реальными сокетами подтвердили двусторонние потери и восстановление. В игровом прогоне `network-probe-20260926-165253-858` на 2× отброшены 20 серверных пакетов за 1000 мс; снимки продолжились с кадра 104 на 125 в прежнем соединении, ошибок декодирования нет. Это основа воздействия, ещё не интегрированная приёмка сетевого сценария: журнал прокси нужно включить в манифест и анализатор, воздействие привязать к этапу, после восстановления проверять свежесть данных и сопровождение. Длительный обрыв с новым handshake и рестарт сервера остаются открытыми.

Дополнительно реализован `cmd/q2netfault-report`: строгий пересчёт журнала без сервера, проверка стадий/времени, обязательного воздействия и восстановления обоих направлений в заданный срок. Тот же игровой журнал принят с задержками 12 мс; обязательная потеря исходящих пакетов корректно отклонена как невыполненная. `go test ./...` прошёл, включая реальный UDP-тест с новым анализатором. Это транспортный отчёт; связь с игровыми кадрами и применёнными командами ещё не реализована.

### Атрибуция пропусков игровых кадров сетевому воздействию

Прокси с `decode_quake: true` записывает идентичность кадров передаваемых и отбрасываемых серверных пакетов. `q2netfault-report` с `bot_trace` проверяет соответствие каждому записанному кадру и требует доказательства для каждого пропуска внутри окна. Необъяснимые пропуски сохраняют `trace_invalid`; разрешение не распространяется на обычный анализатор сессий. Первый вариант ограничен одной картой, поколением и подключением.

Живая проверка `network-frames-20260926-170543-209` на 2× принята: 217 записанных кадров, 20 объяснённых потерь, первый кадр восстановления 125. Намеренное удаление переданного кадра 197 из копии трассы отклонено. `go test ./...` прошёл. Следующий этап — привязка обрыва к готовности сценария и проверка возвращения к сопровождению, затем включение в пакет с манифестом и сверкой исходящих команд.

### Привязка сетевого обрыва к готовности этапа

Реализованы `arm_barrier_dir`/`arm_phase`: прокси ждёт подтверждений обоих клиентов и согласованного игрового кадра, затем начинает отсчёт обрыва. Клиенты и прокси используют общий расчёт `internal/harness/coord`; подтверждения сохраняются в журнале и проверяются анализатором. Живая проверка `network-barrier-20260926-171248-352` на 2×: старт 46 из готовности 24/36, 20 объяснённых потерь, восстановление 9 мс. `go test ./...` прошёл. Приёмка относится к воздействию внутри первого этапа; завершение всей сессии и восстановление сопровождения ещё не проверены. Следующий шаг — движение актёра во время обрыва и проверка реакции после него.

### Следование после сетевого обрыва — первая приёмка

В `q2netfault-report` добавлены `actor_trace` и `follow_recovery_frames`: проверяются движение актёра внутри обрыва, свежая позиция правильного игрока, команда следования и фактическое движение бота в ограниченном окне. Сценарий `network-follow-session.json` сохраняет тестовую постановку. Прогон `network-follow-20260926-172006-881` на 2× принят: перемещение актёра 73, восстановление/наблюдение/следование 86, движение бота 88; 20 сетевых потерь объяснены, задержка транспорта 21 мс. Go-тесты прошли.

Начальная точка на нижнем уровне дала отказ `network-follow-20260926-171831-749` и сохранена в артефактах; естественное восстановление контакта между уровнями остаётся открытым. Принятый тест использует постановку актёра на стартовой площадке и заканчивается по времени внутри первого этапа. Следующий этап — воспроизводимый запуск сетевого сценария в общем пакете, манифесты, ограниченный параллелизм и сверка команд с учётом потерь.

### Классификация отказа анализатора сессии в пакете

Подготовленный запуск сессии теперь может вернуть непринятый отчёт анализатора в пакет без исключения, скрывающего его причину. Перед этим проверяются тип `accepted`, допустимое состояние и соответствие коду завершения анализатора. Самостоятельный запуск по-прежнему завершается ошибкой при отказе. В сводке сохраняются исходное состояние, причина, координаты проблемы, ссылка на отчёт, метрики и время выполнения. Настоящие ошибки запуска/чтения сохраняют `infrastructure_failed` и явное `accepted: false`; отказ проверки не становится успешным прогоном.

Живая отрицательная проверка: `scenario-suite-20260926-164759-528`, две параллельные сессии на 2×, манифест подтверждён. Обычная двухкартовая сессия принята; вариант с обязательным, но отсутствующим reconnect отклонён как `behavior_failed` с причиной `invariant_not_exercised: search_reset_on_reconnect`. Пакет закономерно завершился ненулевым кодом, результат 1/2; это ожидаемое доказательство сохранения отказа. Конфигурация проверки: `workspace/artifacts/session-verdict-suite.json`. Этот шаг относится к отказам уже запущенного анализатора; аварии клиентов до формирования отчёта требуют отдельной диагностики.

Приёмка 2026-09-26: `go test ./...` прошёл; `scenario-suite-20260926-153648-399` — 10/10 принятых прогонов, четыре ожидаемых отказа, 2× и параллелизм 2, `provenance_valid: true`. В отчёте `run-001` у обоих клиентов выделены отдельные сегменты подготовки `base1 → base2` с совпадающими поколениями и без проблем непрерывности. Повторная загрузка той же карты, разрывы, возврат поколения, ошибочное склеивание карт и потеря причины отказа при сбросе кадра покрыты Go-тестами; управляемый переход в середине сценария этим пакетом не проверяется.
