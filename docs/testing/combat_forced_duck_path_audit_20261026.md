# Jail3: фактический присед и проверка пути

26.10.2026. Диагноз исполнения на существующем validation бою, не улучшение качества модели.

## Воспроизведение

Источник: `combat-wide-prior-screen-v1-20261026`, parent U9, jail3 seed1847002396. В первых 300 учебно-совместимых переходах серия нулевой Forward/Side длится 78 кадров; дополнительная завершающая запись native steps не включена в этот счётчик. Кадры 320–397, положение около `[-795.375,-431.875,616.125]`. Бот уже имеет наблюдаемый Ducked=true и посылает Up=0 (release). Положение после начала серии не меняется; это конкретное застревание, в отличие от общего счётчика отменённых команд, где часто сохранялась инерция.

Все восемь standing-hull clearance в локальных probes отсутствуют: `EnrichEnvironment` заполняет их только если стоячий hull свободен в текущей точке. Eye rays и ground-drop при этом присутствуют. Модель получает реальную скорость, ducked/on_ground, предыдущую применённую команду и геометрию. Поэтому говорить о полном отсутствии информации о стенах нельзя. Но текущая причина отмены и предыдущая запрошенная команда не являются явными полями базового feature vector.

`q2support-audit` в frame335: standing trace StartSolid/AllSolid=true; crouched trace оба false; опора dry_flat, центр пола на 0.125 unit ниже стоп. Тест использует канонические BSP `F:/src/quake2/assets/baseq2`; временный runtime исходного запуска уже удалён. Попытки чтения удалённого runtime и корня без baseq2 сохранены в истории; итоговый запрос `request-assets-baseq2.json` явно указывает действительный корень assets.

## Конкретное рассогласование

`predictPmoveGround` правильно повторяет PM_CheckDuck: при Up=0 уже присевший игрок остаётся присевшим, если standing hull пересекает препятствие. Однако `checkedCombatMotionPaths` выбирает hull для проверки сегментов только по `cmd.Up < 0`. Для Up=0 это стоячая коллизия, хотя физический прогноз уже выполнен для присевшей.

На 78 сохранённых состояниях построены 156 геометрических запросов: исходная команда и та же команда с Up=-400. Положение, скорость, yaw/pitch и горизонтальный запрос сохранены. Все 78 исходных прогнозов существуют; исходная проверка пути отклоняет все. При явном crouch проходят все 78. В 74 прогнозах смещение превышает 1 unit; это предсказание, не реально исполненный контрфактический ход. Наличие проверенного пути само по себе не доказывает выигрыш боя.

## Реализовано

В `RecordedMotionAudit` добавлены только диагностические поля `forced_duck_observed` и `proposed_effective_pose_path_checked`. Диагностика требует наблюдаемый присед, release, валидную заблокированную standing-коллизию и валидную свободную crouched-коллизию; проверяет прежнюю физическую траекторию с фактическим hull. Исходная команда и live guard не изменяются.

Физический regression `TestRecordedForcedDuckReleasePathMismatch` использует небольшой fixture `internal/bot/testdata/forced-duck-jail3-frame335.json`. Он проверяет отсутствие мутаций, прежний отказ и новый диагностический допуск, совпадение физического прогноза release/explicit crouch и отказ трактовать jump/explicit crouch/ненаблюдаемый присед как forced release. Neural inference на CPU не выполняется. Вместе с существующими RecordedMotionAudit tests он прошёл на настоящих BSP.

Артефакты: `workspace/artifacts/combat-jail3-blocked-audit-v1-20261026`: support.json, motion-request.json, исходный motion.json, расширенный motion-effective-pose.json, complete.json с SHA.

Итог расширенной диагностики: actual forced-duck=78/78, legacy path checked=0/78, effective-pose path checked=78/78. Сборка `q2motion-audit`, `q2support-audit`, `q2coopbot` и `git diff --check` прошли. Общая `go build ./...` остановлена после более двух минут обхода большого workspace; успешной общей сборкой это не считается. Полный Go test suite с CPU neural inference не запускался согласно требованию CUDA-only; выполнены только указанные физические тесты.

## Следующий эксперимент

Это отличается от прежнего отрицательного `unsupported_motion_guard`/checked-ground опыта: здесь конкретная рассогласованность позы при Up=0, а не общее расширение допуска движения. Следующий этап — отдельный явно отмеченный native diagnostic режим для исходной команды при **наблюдаемом forced duck**, со всеми прежними проверками опоры, траекторий, movers/bodies и без выбора альтернативного направления, auto-crouch или изменения прицела/огня. Сначала доказать фактический присед и смещение в одном шаге, затем whole-battle paired screen. Для обучения потребуется согласованный версионированный execution contract; просмотренные validation траектории нельзя использовать как новые TRAIN. Default guard и основные веса пока не заменены.
