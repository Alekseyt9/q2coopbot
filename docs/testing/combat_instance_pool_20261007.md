# Общий пул боевых прогонов

Пул использует существующий native server + Go client harness, ускорение x2 и холодный перезапуск сервера для каждого боя. Единица очереди — одна сцена, одна замороженная модель и её группа независимых сидов. Четыре сервера и клиента образуют слот; глобальные лимиты 16, 24 и 32 дают соответственно 4, 6 и 8 слотов. Освободившийся слот берёт следующее задание из общей очереди. Задания разных моделей чередуются, поэтому одна модель не занимает всю очередь до завершения своих сцен.

`scripts/run_registered_combat_pool.ps1` принимает несколько frozen execution plans через `-Plans`. Каждый план получает собственный итоговый report и ссылки на реальные вложенные batch roots. Подписи модели, реестра, рецепта, native receipts и исходников проверяются прежним харнесом. Неудачная группа не становится пригодной для PPO. Признак завершённого сбора не означает победу бота.

В `run_registered_combat_training.ps1` добавлено поле конфигурации `pool_instances`. Значение по умолчанию — 4; поддержаны 4, 8, 16, 24 и 32. В каждой эпохе runner компилирует планы для всех моделей, собирает их бои через общий пул, затем отдельно экспортирует и обновляет каждую модель на CUDA. Данные разных моделей не смешиваются; новые веса используются только в следующей эпохе. Оценки моделей до и после обновления также могут выполняться в одном пуле. CUDA-update выполняется отдельно для каждой модели на одной GPU.

PAK-файлы пул не копирует: сохранён прежний механизм общих assets и runtime links, с удалением ссылок после завершённых прогонов.

## Проверка нагрузки

`scripts/benchmark_registered_combat_pool.ps1` замораживает deterministic копии переданных моделей и повторяет одни и те же сцены и validation seeds при разных лимитах. Это проверка планировщика, а не независимый тест качества модели. Отчёт содержит скорость сбора игровых кадров, число пригодных captures, CPU, минимум свободной памяти и фактический пик серверов. Ошибка одного лимита сохраняется и не мешает проверить следующие лимиты.

На первом запуске лимит 16 прошёл 64/64 captures. При 24 обнаружена задержка старта клиента: Windows CIM-запрос готовности UDP-порта выполнялся до запуска клиента, и native server успевал пройти фиксированный release frame 100. Сервер корректно прекращал такой бой; клиент получал disconnect. Подготовка конфига перенесена до запуска сервера, а ожидание готовности заменено прямым UDP `getchallenge`. Проверка фактического loopback binding сохранена после запуска клиента. Фиксированный кадр и условия боя сохранены.

Также исправлен экспорт завершения боя на переходе `control_handoff`: подтверждённый живой последовательный переход принимается как граница сбора, сохраняя truncation и прежний учёт verified kill reward. Переходы обычной логики по-прежнему исключены из on-policy экспорта по owner/provider/sample. Пропуски кадров, смерть и другие неполные переходы не принимаются как победная граница.

Повторная проверка: две версии Temporal attention (Update27 и Update28), восемь сцен, четыре validation seed на сцену и модель, всего 64 боя на каждый лимит. Все восемь геометрических точек base1/base2 представлены; оружие чередуется между Blaster и Machinegun. Партия и подписи моделей одинаковы между лимитами.

24 и 32 отклонены: при высокой нагрузке некоторые клиенты всё ещё проходят signon после фиксированного кадра 100, и native server прекращает бой. Быстрый UDP probe устранил дорогой CIM-query до запуска клиента, но не ограничивает продвижение native clock во время загрузки процесса клиента. Сокращение времени неудачной партии не является ускорением пригодного обучения. RAM не исчерпана. Для устойчивых 24/32 нужен дополнительный native signon barrier либо сокращение/ограничение одновременной подготовки клиентов; в этой проверке они не приняты как рабочие режимы.

Выбран рабочий лимит **16**, он записан в campaign resume config. Это измерение на данной машине и этих сценах, а не гарантия для любой архитектуры. Ресурсные samples включают подготовку и экспорт, CPU отражает общую загрузку машины. При лимите 32 monitor зафиксировал пик 31; лимит очереди был 32. В обучение допускаются только полностью проверенные группы.

## Дополнительная парная оценка

Для остальных восьми рецептов выполнена дополнительная партия на16. В одной группе клиент отправил safety stop без нового кадра при задержке pending native step; сервер правильно отклонил второй шаг. `Client.needsSafetyStop` теперь исключает test synchronous mode: в нём мир уже ожидает подтверждения, дополнительное торможение нарушает контракт. Обычная live safety stop сохранена. Regression test и продуктовые Go tests проходят. Сцена base1 site03 Machinegun повторена для обеих версий в пуле8:8/8 приняты; неудачная и заменённая группы исключены из итога.

Полная проверенная оценка основного CUDA update27→28 теперь содержит128 captures/32 полные группы: [campaign-sites-resume](../../workspace/artifacts/campaign-sites-resume-v1-20261007/report.json). Победы30/64→33/64, смерти31→29. Отдельные source fingerprints, native receipts и SHA всех использованных групп сохранены. Оценка диагностическая, превосходство над rules не доказано. Лимит16 выбран по основной нагрузочной выборке; из этого не следует отсутствие любых сбоев в будущих сценах.

## Рабочий лимит и ожидание подключения

По решению пользователя рабочий глобальный лимит закреплён на **16** серверных инстансах и соответствующих клиентах. Новые замеры на24/32 не запускаются. Пул продолжает распределять разные случаи и модели между четырьмя слотами по четыре независимых боя.

Для isolated synchronous fixtures native server получил опциональный `sv_test_signon_hold_frame=40`: до подключения заданного клиента мир останавливается на кадре40, сетевой signon продолжает обслуживаться. Действуют прежние ограничения isolated loopback harness/cheats/lockstep, combat barrier, один клиент и фиксированный release100; обычные серверы без cvar не меняются. После подключения работает прежний lockstep. Все generated combat fixtures также используют `combat_only`, чтобы не рассчитывать маршрут выхода из карты при подготовке отдельного боя.

Проверка с искусственной задержкой запуска клиента8 секунд: native log подтвердил ожидание на40 и `g_test_combat_start game_frame=100 ready=1`; native стартовые позиции подтверждены, клиент завершился с `frame_gaps=0`, `decode_errors=0`, один монстр убит. Это проверка запуска, не PPO capture. Старый solo gameplay-критерий Shotgun дал accepted=false для Blaster; это не считается успешной оценкой качества модели. Артефакты: `workspace/artifacts/combat-signon-delay-probe-v2-20261007`.

Новая смешанная конфигурация `mixed-campaign-generated-resume-v1.json` включает все20 семейств:16 кампанийных рецептов и4 прежних Parasite/Gunner. Повторный experiment `combat-mixed-registry-resume-v2-20261007` использует80 train battles (offset12) и160 paired validation battles (offset4), pool16 и CUDA-only update. Первая попытка v1 прервана до экспорта/обновления из-за позднего подключения в старых сценах; её данные не использованы для обучения. До завершения v2 вывод о качестве не делается.

Поле `evaluation_seed_offset` в training runner задаёт общий offset validation cohort для обеих версий модели; при отсутствии сохраняется0. Training seeds и evaluation seeds остаются в разных registry splits.

Уточнение после полного mixed capture v2: ожидание signon должно работать только до первого `cs_spawned` клиента данной generation. Иначе после disconnect оно могло удержать мир с последним `pending` шагом без phase=end. Добавлен generation-scoped `test_signon_completed`; после первого подключения signon hold больше не включается. Native executable пересобран. Сообщение Go parser о неполном логе теперь содержит pending/steps/release/effects для диагностики; критерий полноты сохранён. Для synchronous solo runs увеличен wall-time запас до max(60s, frames/10+30s), игровой бюджет и ускорение x2 сохранены.

v2 также остановлена до CUDA-update; частичные captures не использованы. Повтор после этих исправлений: `workspace/artifacts/combat-mixed-registry-resume-v3-20261007`, те же train offset12 и validation offset4. Результат фиксируется только после строгого завершения всех групп.
