## Диагностика движения и горизонтального прицела

`scripts/diagnose_combat.py` читает проверенные batch reports и `dataset/steps.jsonl`, сохраняет SHA входов. Только owner=provider, life=1. Движение измеряется между последовательными кадрами той же жизни: величина предложенного planar action >0.05 и displacement <0.5 units означает запрос движения без фактического перемещения. Applied planar magnitude <0.02 отдельно считается обнулением команды. Максимальная серия разрывается на пропуске кадра/смене жизни. Эти метрики не являются доказательством причины остановки; collision guard и native collision могут вносить разный вклад.

Прицел: ближайшая наблюдаемая clear-shot цель, горизонтальное направление её текущей relative position против view yaw + applied yaw delta. Не учитывает pitch, будущую позицию, скорость снаряда, момент выстрела или факт попадания. Это измерение направления команды атаки, не shot accuracy. Visibility unknown не принимается за clear.

| Режим | Запрошено движение, но displacement <0.5 | Applied движение обнулено | Атака с clear целью и yaw error >15° |
| --- | ---: | ---: | ---: |
| До | 803 / 998 motion pairs | 805 / 1001 provider steps | 854 / 999 visible attack steps |
| После | 787 / 986 motion pairs | 799 / 989 provider steps | 290 / 986 visible attack steps |

После обучения три эпизода стоят подряд 228–233 кадра (~22.8–23.3 игровых секунд при tick 0.1 с). В одном из них 222/274 команд атаки имеют yaw error >15°. Значит накопление опыта ещё не решило выход из остановки и устойчивое удержание цели. Меньшая ошибка по двум другим seeds не подтверждает перенос навыка.

Диагностика текущего цикла выполнялась после сбора. С этого изменения runner замораживает diagnoser SHA/копию и автоматически пишет `diagnostics.json` после evaluation. Четыре focused tests проверяют wrap yaw, applied delta, неизвестную visibility, разрыв кадров/жизней, ownership и фактическое перемещение; прошли. PowerShell syntax и whitespace checks прошли. Go код в этом продолжении не менялся.

## Исправление критерия узкого fixture

Обнаружено: `gameplay_accepted` прежнего tactical harness проверяет rules-specific Shotgun→Blaster request и aim/move ownership правил. Learned policy с фиксированным Blaster не обязана выполнять эту последовательность. Старые report остаются неизменными: это legacy метрика, не критерий качества learned policy.

После завершения цикла `fixture_promotion_eligible` в runner исправлен: все четыре after-capture валидны, native first-life kills ≥1 и нет first observed death. Не требует legacy rules-сценария и не включает модель автоматически. В текущем цикле false и по старому, и по исправленному критерию, поскольку kills=0. Прежний root report фиксирует исходный критерий; исправленный применяется к следующим циклам.

Перед дальнейшим увеличением объёма нужно проверить распределение обучающих примеров выхода из статической блокировки и удержания цели после движения. Изменять reward или подбирать модель по этим четырём evaluation seeds нельзя без отдельного train/development split и новой контрольной группы.
