# Ускоренные прогоны Go-бота

`scripts/run_speed_trial.ps1` запускает обычный сервер Quake II `baseq2`, затем двух Go UDP-клиентов: неподвижного `TestHuman` и проверяемого `GoCoopMate`. Нативный Gladiator Botlib и его игровой мод не используются. Для маршрутизации Go-клиент читает AAS-файл карты из `baseq2/maps`; AAS не загружается сервером.

Нужны Go 1.23+, runtime с `q2ded.exe`, стандартной `baseq2/game.dll`, игровыми PAK-файлами и AAS-файлом тестовой карты. Данные игры не входят в репозиторий. `scripts/prepare_runtime.ps1` создаёт отдельный `workspace/runtime/q2go`, копируя **только** PAK/AAS из каталога с игровыми данными и подставляя `game.dll` из исходников Yamagi. Полноценные AAS из другого каталога можно подключить через `-AASRoot`; скрипт отвергает файлы без таблицы переходов. Это важно: ранее каталог с названием `q2coopbot-runtime-vanilla` фактически содержал Gladiator DLL. Опциональная реконструкция `workspace/tools/bspc` собирается отдельно через корневой CMake, но пока выдаёт AAS без переходов и не годится для маршрутизации.

```powershell
cmake --build F:\src\quake2\yquake2\build\codex-speed-test --target q2ded game
./scripts/prepare_runtime.ps1
./scripts/run_speed_trial.ps1 -Map base1 -GameFrames 100 -SynchronizedStart -UnlimitedLoopbackRate
```

Указанные два переключателя работают с отдельной тестовой сборкой Yamagi. `sv_test_start_client` удерживает игровую логику до входа бота и сообщает о готовности, `sv_test_unlimited_loopback` снимает сетевой лимит только для `127.0.0.1`, а `sv_test_trace_client` регистрирует команды непосредственно перед серверным `ClientThink`. Без этих переключателей скрипт можно запускать с обычным сервером, но проверка принятых команд недоступна. Скрипт занимает свободные последовательные UDP-порты, собирает Go-исполняемый файл в каталоге отчёта, сохраняет журналы и JSONL-трассы и останавливает только запущенные им процессы.

`summary.json` содержит скорость игровых кадров, пропуски снимков, ошибки декодирования, наличие напарника и число отправленных/применённых команд. Базовая проверка требует завершения по числу кадров, отсутствия пропусков и ошибок и наблюдения второго клиента; тестовая сборка дополнительно требует, чтобы каждая отправленная команда достигла `ClientThink`. Совпадение траекторий 1×/2× пока не является критерием: обычный сервер не обеспечивает одинаковое начальное состояние двух независимых запусков. Для такой приёмки нужны детерминированные сценарии и сравнение событий дверей, лифтов и перехода карты.

Повтор **с проверенной стандартной DLL Yamagi** на `base1`, 100 игровых кадров: 1× — 9,84 кадра/с за 10,33 с; 2× — 19,59 кадра/с за 5,19 с. В обоих прогонах Go увидел второго клиента, не было пропусков кадров или ошибок декодирования, сервер принял все 101 отправленную команду. Предыдущий замер в каталоге `q2coopbot-runtime-vanilla` не доказывал независимость от Gladiator и заменён этим результатом.

Диагностический переход карты запускается с `-TransitionMap base2 -TransitionAfterFrames 10 -GameFrames 20 -SynchronizedStart -UnlimitedLoopbackRate`. Go обрабатывает `reconnect` через новый UDP-канал и повторное `getchallenge/connect`; после переподключения откладывает `begin`, чтобы карта начала получать кадры. Трасса хранит имя карты, `spawncount` и номер кадра эпизода, поэтому команды с одинаковым сетевым номером на разных картах сверяются независимо. Через 10 реальных секунд без нового кадра срабатывает `transition_timeout`, а скрипт завершает прогон ошибкой. Для перехода скрипт требует тестовую сборку сервера с командой `sv_test_map_entry`: она принимает карту назначения и карту входа отдельными аргументами, а затем передаёт игровому коду `base2$base1`.

Причина прежнего зависания второго `ClientBegin` локализована: при обычном `map base2` игровая DLL получает пустую точку входа; её резервный поиск кооперативного spawnpoint может бесконечно повторяться. У `base2` есть именованные точки входа `base1`. Передача `base2$base1` непосредственно через RCON не работает из-за раскрытия `$base1` консольным парсером, поэтому тестовая команда сервера собирает строку после разбора аргументов. Стандартная `baseq2/game.dll` не менялась.

Совместный тестовый переход `base1 → base2` **принят** на 1× и 2×: оба Go UDP-клиента переподключились, `GoCoopMate` увидел `TestHuman` уже на `base2`; за 20 кадров новой карты получено 9,40 и 19,18 кадра/с, весь сценарий занял 5,09 и 3,28 с. В каждом прогоне нет пропусков кадров и ошибок декодирования, все 32 отправленные команды на обеих картах совпали с командами, принятыми `ClientThink`. Артефакт: `workspace/artifacts/transition-coop-clean-20260925/summary.json`. Скрипт теперь отдельно требует `teammate_seen_after_transition`, поэтому наблюдения напарника только на `base1` недостаточно. Это принудительный тестовый переход; естественный выход с уровня ещё не проверен. На момент этого прогона `base2.aas` в runtime не было, поэтому маршрутизация на новой карте в нём не проверялась.

Затем `base2.aas` с переходами был импортирован из локального архива игрового runtime и проверен с `-RequireTransitionAAS`. На `base2` Go загрузил 3248 областей и 4283 поддерживаемых маршрутизатором перехода; состояние маршрута стало `ready` на обоих скоростных режимах. Получено 9,52 и 18,62 кадра/с, 4,99 и 3,28 с на весь сценарий; обе проверки снова подтвердили все 32 команды. Артефакт: `workspace/artifacts/transition-coop-aas-valid-20260925/summary.json`. Архив `aas-work/q2-campaign-20260920/aas` был создан оригинальным `bspc.exe` 1.4: в нём есть геометрия и области, но ещё нет таблицы переходов. Журнал прежнего runtime показывает следующий этап: BotLib рассчитывал переходы при загрузке карты и записывал обновлённый AAS. Текущая реконструкция `workspace/tools/bspc` пока записывает только заголовок и габарит игрока, остальные секции пусты. Проверка `ready` показывает загрузку графа и маршрут к текущему близкому напарнику; прохождение сложного маршрута, двери и лифты она ещё не доказывает. Следующий шаг — естественный переход с уровня и отдельные сценарии навигации.
