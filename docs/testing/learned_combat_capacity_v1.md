# Сравнение ёмкости MLP: 64 / 128 / 256

05.10.2026. Замороженный пилот, а не доказательство необходимого размера сети. Root: `workspace/artifacts/combat-capacity-v1-20261005`. Во всех вариантах два скрытых ReLU слоя, вход 386, выход actor 8, critic 1 и четыре обучаемых log_std. Всего параметров: 58445 / 133261 / 332045.

Общий родитель — четвёртый update curriculum HP20, SHA256 `9920296b170acaa1f184f61ea900d6579af88b4999978ce1e76d9bbbd76cb01b`. Новые варианты получают сохранённую функцию через дублирование hidden units и распределение outgoing weights между копиями. Положительные неравные доли суммируются до единицы и позволяют градиентам копий различаться. Это вариант function-preserving widening из [Net2Net](https://research.google/pubs/net2net-accelerating-learning-via-knowledge-transfer/); проверка float32 parity на существующих rollout обязательна, но не доказывает совпадение на всех возможных входах. Offline Python только переносит и обучает веса, runtime остаётся Go.

Обе Adam истории сбрасываются **во всех трёх вариантах**, включая 64×64 контроль. RNG, log_std, objective, consumed-rollout history и накопленные counters сохраняются. Обычное продолжение родительского Adam не используется как контроль. Старые rollout используются только для проверки выходов, не для обучения. Лимит Go загрузчика расширен до hidden width 256 и файла 16 МБ; более широкие модели по-прежнему отклоняются.

Протокол заранее: каждый вариант получает четыре fresh batch × четыре инстанса × 300 игровых кадров, x2, fixed fourth update. Тренировка на Parasite 20 HP с reward v2, парная оценка до/после на обычном 175 HP. Training seeds 14700–14715, eval 14800–14803. Внутри batch каждый инстанс имеет отдельный seed; между архитектурами seeds совпадают для сопоставимости. Последовательный запуск трёх вариантов использует максимум четыре сервера/клиента одновременно. Бюджет игровых кадров и предложенных optimizer steps одинаковый; число usable переходов и принятых KL-limited шагов может различаться. CPU/CUDA выбирается по существующему измерению на каждом batch.

Критерии: native first-life kills, исходящий/полученный урон, deaths, diagnostics движения и горизонтального прицела, measured selection p95/p99. Не выбирать checkpoint по лучшему результату eval. Одна геометрия, один противник и четыре eval пары на вариант не устанавливают статистический эффект или обобщение. Автоматической замены пользовательского live нет. GRU/LSTM рассматриваются отдельным этапом плана, не смешиваются с этим сравнением ширины.

Проверки перед запуском: тесты переноса на ненулевых входах, сохранение состояния родителя и RNG, воспроизводимость, запрет shrink/mismatched checkpoint; Go загрузка/Decide/Review для 64/128/256, запрет 257 и обход прежнего лимита файла. PowerShell syntax проверяется штатным parser.

## Завершённый пилот

Все три цикла завершились штатно. Общий `go test ./...`, четыре Python unit tests (capacity и импортированные exploration проверки), PowerShell parser и `git diff --check` прошли. Погрешность переноса на 551 probe кадре: actor до 1.91e-6, value до 3.58e-7. Go native replay каждого свежего rollout подтвердил actor/value/log-probability для соответствующей ширины. Все 72 capture complete/provenance valid/dispatch valid/seed confirmed. CUDA доступна, но CPU оказался быстрее на всех 12 небольших тренировочных batch.

Смертей на всех eval 0. Суммы относятся к четырём first-life эпизодам каждого варианта. Все 46 positive kill reward windows сопоставлены с provider-owned step и **включённым PPO rollout**, score совпал. Итоговые принятые actor steps по batch: 64 — 5/4/4/8; 128 — 4/5/10/9; 256 — 4/5/4/5. KL каждого update не превышает 0.01. Бюджет предлагаемых шагов одинаковый, принятые шаги ограничены KL и поэтому различаются.

Максимальный episode selection p95 среди восьми eval до/после: 1.021 / 1.054 / 2.103 мс соответственно. Это максимум отдельных квантилей эпизодов, не pooled p95 и не задержка одного только матричного слоя. Подробные p95/p99/max и SHA исходных доказательств сохранены в `audit.json`.

Начальная функция сохраняется в пределах численной проверки, но начальные игровые результаты различаются между arms. Аудит `evaluation-before` показал: для 128 vs 64 на seeds 14801/14802 здоровье расходится в observation шага 24/74, а первые различия sent commands появляются **на этих же шагах после этого observation**. Предыдущие команды совпадают. Для 256 аналогичное наблюдение на 14800/14801/14802 (26/24/74). Причина полного расхождения engine state этим аудитом не локализована. Это подтверждает ограничение прежнего observed-reset proof: seed и совпадающая история команд не обеспечивают воспроизводимость всех скрытых состояний/таймингов движка.

Вывод: ни одна ширина не научилась добивать полного Parasite, победитель по ёмкости не установлен. HP20 слишком лёгок: большинство тренировочных боёв заканчиваются за три provider кадра; положительные kills почти не дают опыта длительного сопровождения. Нельзя интерпретировать 84/428 переходов, разные начальные игровые траектории и четыре eval пары как доказательство нужного размера сети. Приоритет перед следующими сравнениями — более длительное упражнение прицела/добивания и локализация невоспроизводимости world reset. GRU и attention остаются отдельными запланированными экспериментами.
