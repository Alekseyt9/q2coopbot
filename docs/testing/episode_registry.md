# Реестр эпизодов

`episodes.json` — единый список наблюдаемых ошибок, включая ещё не воспроизводимые. Сценарии лежат в `scripts/scenarios`, исходные трассы и результаты — в игнорируемой `workspace/artifacts`. Без сохранённых локальных артефактов историческую трассу нельзя восстановить из Git; JSON-сценарии доступны из репозитория.

Каждая запись содержит ID, карту, симптомы, статус исправления, готовность воспроизведения, сценарий, исходное свидетельство, недостающую подготовку и критерий приёмки. `observation_only` никогда автоматически не считается проходящим тестом. `ready` означает готовность запустить воспроизведение, а не исправленность ошибки.

Команды из корня проекта:

```powershell
./scripts/run_episode_regressions.ps1 -List
./scripts/run_episode_regressions.ps1 -Id base2-bridge
./scripts/run_episode_regressions.ps1 -Id base1-stairs,base2-bridge -Timescales 1,2
```

Runner собирает текущего бота один раз, запускает существующий UDP-харнес последовательно на отдельном тестовом порту, сохраняет копию реестра и `report.json`. Текущая человеческая сессия не используется. Для приёмки проверяются серверные команды через штатный runner, затем фактическая позиция живого бота на земле, требуемое событие и возобновление движения. Успешного старта сервера либо выбора цели недостаточно. Ненулевой результат блокирует E2E-приёмку. Это пока не детерминированное восстановление полной сохранённой игры и не замена suite/provenance-манифестам.

При новой ошибке сначала сохраняем трассу, добавляем `observation_only`, перечисляем недостающие условия. После появления точного сценария и исполняемого критерия переводим в `ready`. Статус исправления меняем только по проверенным результатам; runner сам реестр не переписывает.

Дополнения формата: сценарий может задавать `bot_health` (1..100), `map_entry` (например base2a для base3) и `bot_invulnerable` (только изолированный тест). Реестр поддерживает `kind: session`, проверяет SHA256 обязательного AAS и не принимает отсутствие начального здоровья/позиции за успешную подготовку. Обычный клиент не использует тестовые параметры без их явного указания.

### Повторная лестница base3, 26.09.2026

`base3-stairs-20260926-190951` воспроизводится после подбора актором двух аптечек у лестницы. Простая расстановка на свежей карте проходит даже на старом бинарнике и не является воспроизведением. Отказ сохранён в `workspace/artifacts/base3-stairs-both-health-baseline`: бот с 44 HP остаётся внизу, меняя цель между аптечками и игроком; на кадрах 248–251 направление движения меняется каждый кадр. Это поведенческое воспроизведение, не восстановление всей сохранённой игры.

Исправление удерживает выбранную видимую аптечку при выходе за радиус первоначального выбора 300 units и появлении более близкого предмета. Исчезновение предмета и прежний таймаут отсутствия прогресса освобождают цель. Сценарий `base3-stairs.json` использует защиту бота от урона, здоровье 34 и `actor_health: 50`; последовательные контрольные точки здоровья актора 60/70 подтверждают подбор обеих аптечек. Runner проверяет их через `acceptance.actor_health_checkpoints`, затем подъём бота к игроку. Это приёмка навигации, не боевого выживания.

Для дальнейшей диагностики JSONL теперь содержит `goal_point`, оставшийся `route` и наблюдаемые `pickups`. Старые трассы этих данных не содержат. Эпизоды `base3-elevator-20260926-191435` и `base3-lost-20260926-192240` открыты. Простая расстановка из `base3-elevator.json` проходит и пока не воспроизводит зависание перед лифтом; необходима история подхода/платформы. Новую телеметрию текущий живой процесс получит только после обновления бинарника и перезапуска.

Приёмка: `episode-regressions-20260926-192453-770/report.json` — 8/8 (новая лестница base3, лестница base1, оба старых случая аптечек на 1×/2×). Повтор с обязательными контрольными точками подбора аптечек актором: `episode-regressions-20260926-192807-520/report.json` — 2/2. `go test ./...` прошёл. Новое наблюдение `base2-stuck-20260926-192906` остаётся открытым: 38 HP, ожидание игрока, причина потери контакта ещё не установлена. Исправление лестницы и новая телеметрия не установлены в продолжающуюся пользовательскую сессию.

### Лифт и выбор цели огня, 26.09.2026

- `base3-elevator-20260926-191435`: в replay исторической трассы на кадре 3255 состояние лифта переживало замену маршрута обычными точками. Это блокировало дальнейшее перестроение и оставляло бота у точки этажом выше. Замена маршрута теперь освобождает связанный манёвр лифта; его запуск также очищает наземный detour. `TestRouteReplacementDropsOldElevator` проверяет это без игровых ресурсов. Опциональный `TestElevatorLiveTraceAudit` воспроизводит нарушение до исправления и проверяет инвариант после него; требуются `Q2_ELEVATOR_TRACE` (исходная trace.jsonl) и `Q2_SEARCH_SCAN_ROOT` (baseq2). Это replay восприятия, не замкнутый физический E2E; старая трасса не содержит pickups/оружие/патроны.
- Сценарий `base3-elevator.json` включает совместный подъём, промежуточную точку у выхода и уход игрока. На 2× текущая версия возвращается к сопровождению без оставшегося состояния лифта (`base3-elevator-cover-fixed`), старая версия сохраняет `approach` даже после возвращения к игроку (`base3-elevator-cover-old`). Точный исходный срыв под платформу этим сценарием пока не воспроизведён: статус `fixed_pending_e2e` сохранён.
- Контрольный ElevatorTrial на 2× с архивным `aas-base2-elevator-final-20260925` прошёл `board → ride → exit → landing_probe → landing_unconfirmed → completed`, высота от −37.875 до 112.125 (`elevator-route-owner-fixture-2x`). Нельзя выдавать архивный AAS за приёмку актуального runtime.
- `bunk1-no-fire-20260926-193729`: 409 кадров без атаки содержат закрытого ближайшего монстра и другого видимого монстра ближе 650 единиц. Выбор теперь ранжирует только подтверждённые линии огня.
