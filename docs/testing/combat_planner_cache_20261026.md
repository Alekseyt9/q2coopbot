# Ускорение подготовки зарегистрированных боёв

26.10.2026. `registered_combat_planner.ps1` собирает metadata CLI `q2episode` один раз и хранит его в `workspace/build/registered-planners/`. Ключ зависит от полного harness source fingerprint и версии Go; receipt содержит SHA бинарного файла. Проверяется привязка каталога к репозиторию, executable/receipt и неизменность исходников до/после подготовки. Публикация нового каталога атомарна; частичные сборки и неудачные проверки не заменяют успешный кэш.

`run_registered_combat_episodes.ps1` по умолчанию использует этот CLI; `-LegacyPlanner` оставлен для сравнения с прежними двумя `go run`. Episode и cohort pool передают один source-bound context всей подготовке. Сам `--verify-plan` вызывается заново для каждого плана: Go заново загружает и валидирует все descriptors, пересоздаёт выбранную task и сравнивает все условия/привязки. Проверки model/index/episode/runner/reward, диапазонов seed и modes сохранены.

Основная экономия получена также от переиспользования каталога эпизодов внутри одного context. Полный вывод `--list` содержит 612 эпизодов и около 21 МБ JSON; его вывод/PowerShell-разбор раньше повторялись для каждого плана. Кэш каталогов привязан к абсолютному пути и SHA индекса. Изменение descriptor при прежнем index SHA обнаруживается свежим `--verify-plan`, даже если каталог уже разобран. Это проверено отдельным private-registry regression. Кэш не меняет игровую политику или вычисления обучения; нейросетевых Go-проверок здесь нет.

## Проверки и замеры

Артефакты: `workspace/artifacts/combat-planner-cache-v1-20261026/`.

- `checks-v2/report.json`: на восьми исторических планах с восьми карт старый и новый режимы принимают одинаковые планы и возвращают одинаковый текст. Шесть invalid/stale вариантов отклонены обоими: registry/model/runner/episode SHA, seed и изменение descriptor после прогрева каталога.
- Изменение бинарного файла и исходников отклоняется в отдельном частном fixture, без повреждения рабочего кэша.
- Замер восьми планов: **23.13 → 6.35 с**, **3.64×**. Это сравнительный замер подготовки с сохранением проверок, не ускорение игрового времени.
- `dryrun-96.json`: полный preflight 96 планов — **53.84 с**. В предыдущей серии от создания collect.log до первого native job прошло около **292 с**. Последние два числа относятся к разным запускам, а не строгому A/B всей игры.
- `live-v2-pool/report.json` и `live-cuda-batch/report.json`: **4/4 native и 4/4 CUDA**, source unchanged; native pool 36.10 с, 16 слотов, ×2, четыре разных мира/seed. Это живая интеграционная проверка; качество модели не сравнивалось.

Первая live-попытка сохранена failed: launcher не передал `Q2COOPBOT_DIAGNOSTIC_ENGINE_ROOT`, поэтому необходимые objective-сценарии остановились до игры. Повторены все четыре случая в fresh v2 каталогах с существующим objective-capable engine. Исходники/сценарии не ослаблялись ради прохода.

## Использование в следующем сборе

`run_combat_wide_future_registry_expand.py` запускает 108 native/CUDA ветвей для следующих 12 SHA-selected teacher состояний на 10 картах, исключив прежние восемь состояний. Отбор не использует победы или предпочтения. Каждый мир имеет отдельный исходный seed; два suffix seed дополнительно выводятся из SHA(record_id, future) и совпадают только между сравниваемыми действиями одного мира. Сброс начинается на root+1. Сохраняются original, forkA/forkB и baseline/choice0/choice1.

План предусматривает `uncertainty-evidence.json`: среднее и sample stddev только при отсутствии hybrid во всех трёх продолжениях, все индивидуальные contrasts, ничьи, mixed control и limited evidence. Три продолжения не дают гарантии точной Q-оценки. Targets и новые actor weights автоматически не выпускаются; обычным PPO этот диагностический сбор не является. Каталог запуска: `combat-wide-future-registry-expand12-v1-20261026`; его завершение следует проверять по фактическим процессам и `complete.json`.
