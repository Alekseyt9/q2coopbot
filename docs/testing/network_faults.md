# Управляемые потери UDP

`cmd/q2netfault` — отдельный прокси между одним клиентом и локальным сервером. Политика бота не получает команды reconnect: прокси на заданное время отбрасывает пакеты в обе стороны, затем снова передаёт их. Игровой сервер и остальные прямые клиенты продолжают работу.

Сборка: `go build -o workspace/build/q2netfault.exe ./cmd/q2netfault`.

Запуск: `workspace/build/q2netfault.exe --config <путь-к-конфигу>`.

Пример конфига в свежем каталоге артефактов:

```json
{
  "listen": "127.0.0.1:29061",
  "server": "127.0.0.1:29060",
  "after_ms": 4000,
  "duration_ms": 1000,
  "run_ms": 15000,
  "events": "network.jsonl"
}
```

Сервер слушает `127.0.0.1:29060`, клиент подключается к `127.0.0.1:29061`. Прокси печатает `relay ready` после открытия обоих сокетов. Обрыв начинается через `after_ms` после первого пакета сервера, включая handshake; отсчёт не привязан к готовности игрового этапа. Миллисекунды реальные, ускорение сервера их не меняет. `run_ms` ограничивает общую жизнь процесса, включая ожидание клиента.

JSONL содержит направление, стадию (`unarmed`, `before`, `blackout`, `after`), действие (`forward`, `drop`), длину и номер последовательности для пакетов с сетевым заголовком. Содержимое пакетов не сохраняется. Существующий файл журнала не перезаписывается. Отказ записи прерывает прокси. Допускаются только явные IPv4 loopback-адреса; первый клиент закрепляется, другой исходный endpoint вызывает отказ. Миграция endpoint при reconnect пока не поддерживается.

Нулевой код выхода означает нормальное завершение транспорта, не приёмку поведения или факт срабатывания обрыва. Нужно проверить наличие отброшенных пакетов и последующей передачи; для каждой стороны отдельно. Если клиент не отправлял пакеты во время обрыва, его исходящие потери не были задействованы.

Приёмка транспорта: `go test ./...` включает тест с настоящими UDP-сокетами, передачей бинарного содержимого без изменений, потерями в обоих направлениях и восстановлением. Граничные моменты интервала проверены отдельно.

Игровая проверка `workspace/artifacts/network-probe-20260926-165253-858`: сервер 2×, один неподвижный клиент, обрыв 1000 мс. Отброшены 20 серверных пакетов; запись кадров возобновилась с 104 на 125 в прежнем соединении 1, всего 215 строк, ошибок декодирования 0. Исходящих пакетов во время обрыва не было. Эта проверка не подтверждает сопровождение после обрыва, новый handshake или восстановление после рестарта сервера.

Следующий этап: включить прокси в изолированные пакетные сессии и манифест; привязать воздействие к готовности этапа; анализировать журнал потерь вместе с трассами и серверными применёнными командами. Обычную проверку непрерывности нельзя просто отключить: разрешать только разрывы, объяснённые доказанным воздействием. После обрыва нужен ограниченный бюджет получения свежих снимков и возобновления сопровождения. Необъяснимые потери должны оставаться отказом.

## Автоматическая проверка транспорта

`go run ./cmd/q2netfault-report --config <report-config.json>` пересчитывает отчёт без игрового сервера. Пример конфигурации рядом с журналом:

```json
{
  "network": {
    "listen": "127.0.0.1:29061",
    "server": "127.0.0.1:29060",
    "after_ms": 4000,
    "duration_ms": 1000
  },
  "events": "network.jsonl",
  "output": "network-report.json",
  "recovery_ms": 500,
  "require_upstream_loss": false
}
```

Анализатор проверяет обязательные поля, порядок времени, начало отсчёта первым серверным пакетом, соответствие стадии заданному интервалу и действия стадии. Нужны пакеты с номером последовательности до и после обрыва в обе стороны и наблюдаемые потери серверных пакетов. `require_upstream_loss: true` дополнительно требует потери клиентских пакетов. OOB handshake сам по себе не заменяет этот трафик. `recovery_ms` — предел от конца заданного обрыва до первого переданного пакета с номером последовательности, для каждого направления отдельно.

В отчёте доступны количества передач/потерь, пакеты с номерами до/во время/после обрыва и задержки восстановления. Повреждённый журнал получает `trace_invalid`; невыполненное воздействие или отсутствие своевременного восстановления — `fixture_failed`. Отказ сохраняет отчёт и завершает команду ненулевым кодом. Файл вывода не может совпадать с журналом или конфигурацией.

Повторный анализ `network-probe-20260926-165253-858` принят с 20 потерянными серверными пакетами и задержками восстановления 12 мс в обе стороны. Отдельная проверка того же журнала с `require_upstream_loss: true` закономерно отклонена с `client_to_server: loss not exercised`. Go-тесты включают повреждённые/неполные записи, несогласованные стадии, отсутствие потерь/восстановления, превышение срока, а также анализ журнала настоящего UDP-теста.

Это отдельная приёмка транспорта: успешная отправка прокси не доказывает декодирование игрового снимка клиентом или применение команды сервером. Отчёт пока не разрешает разрывы в обычном анализаторе сессии; объединение этих доказательств остаётся следующим этапом.

## Связь потерь с игровыми кадрами

Опция `decode_quake: true` в конфиге прокси включает пассивный разбор серверного потока, включая отбрасываемые пакеты. В события записываются `frames` с картой, `spawncount` и номером кадра; ошибки разбора сохраняются как `decode_error`. Штатный `svc_disconnect` помечается `control: disconnect`; его последующее сообщение также разбирается. Это наблюдатель протокола, решения клиента он не меняет.

Поле `bot_trace` в конфиге `q2netfault-report` включает дополнительную проверку `game`. Каждый записанный кадр клиента должен иметь переданный пакет прокси. Каждый отсутствующий кадр между первым и последним кадрами трассы должен иметь пакет, отброшенный во время обрыва, без подтверждения передачи того же кадра. Отсутствующий переданный кадр, ошибка декодирования или отсутствие соответствующего сетевого события отклоняют отчёт. Требуется реально наблюдаемый разрыв и восстановление после него. Сейчас проверка ограничена одной картой, поколением и подключением; обычный анализатор сессий не получил общего разрешения пропускать кадры.

Приёмка `network-frames-20260926-170543-209`: сервер 2×, 217 записанных кадров, все 20 отсутствующих кадров объяснены потерями прокси, первый восстановленный кадр 125. Транспорт возобновился через 34 мс после конца обрыва. Копия трассы с дополнительно удалённым переданным кадром 197 отклонена как `trace_invalid: unexplained missing frame 197`. Предыдущий прогон `network-frames-20260926-170346-048` сохранил отказ наблюдателя на штатном `svc_disconnect`; обработка исправлена до финального прогона. `go test ./...` прошёл.

Эта проверка подтверждает приём записанных игровых кадров в пределах окна трассы. Применение исходящих команд, возвращение к сопровождению, потери вне окна и интеграция с барьером этапов/параллельным пакетом остаются отдельными работами.
