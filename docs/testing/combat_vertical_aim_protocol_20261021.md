# Следующий опыт: прицел после выбранного crouch/jump

Статус: v2 реализован, нулевая миграция проверена на CUDA и в игре, обе BC ветки обучены на GPU. Smoke24 native/16 CUDA и screen72 native/48 CUDA закрыты. Кандидат не продвигается после отрицательного screen. Протокол ниже был зафиксирован до обучения; выполненные проверки описаны в конце.

## Основание

В [native диагностике](combat_native_ballistic_geometry_20261021.md) выбранный crouch/выход из crouch меняет muzzle примерно на24 units в текущем шаге. Ветка sampled-motion v1 видит выбранные forward/side, но не vertical. На независимых development seeds дополнительный vertical уменьшил RMSE отдельного прогноза высоты ствола9.72→5.47 units. Это полезность входа для вспомогательного прогноза, не улучшение политики.

## Изолированное изменение

Сначала проверить минимальную one-hot модификацию125→128 входов с прежними64/32/2 слоями. Новые три столбца инициализировать нулями; одинаковая архитектура для контрольной ветки и кандидата. Контроль получает три нуля, кандидат — выбранные release/jump/crouch. В контроле новые столбцы остаются замороженными нулевыми. Остальные входы, положение учебной точки внутри bbox, награда, шум, guards и физика остаются одинаковыми между ветками. Не добавлять ручную компенсацию угла или запрет движения.

Новая версия модели должна явно обозначать контракт128. Старые v1 файлы продолжают загружаться как125. Политика имеет joint likelihood с aim, условным на target/mode/movement/vertical. Вертикальную команду выбрать до вычисления окончательного aim, сохранив прежний порядок чтения RNG: заранее сохранить шумы yaw/pitch и применить их после выбора vertical. Review использует записанный vertical. Retention суммирует категории vertical по вероятностям teacher; движение по-прежнему использует закреплённую behavior выборку. Нельзя молча подставить vertical=release в старый likelihood.

## Проверки до обучения

На CUDA: исходные средние, likelihood, actor/value/std и Adam states сохраняются после нулевой миграции; размер входных моментов расширяется нулями. Проверить восстановление checkpoint. Ненулевой probe должен менять только выбранный vertical residual и корректно менять likelihood/retention; target=None нейтрален. Численные NN тесты только CUDA. В Go — валидация контрактов и сборка; исполнение NN проверять в настоящем native прогоне с CUDA replay.

Для BC разрешён существующий train corpus с исправленной release разметкой (`combat-sampled-motion-labels-release-v2-20261021`),1239 train/641 development labels до фильтров. Его исходный zero-v1 checkpoint должен быть явно закреплён как источник histories. Миграция доказывает эквивалентность на этих histories; нельзя подменять model_sha в старых метаданных под новый checkpoint. Evaluation/coverage данные в fit не попадают.

## Ограниченный бюджет и решение

Две ветки из одной нулевой миграции, одинаковый GPU seed,80 фиксированных BC steps,lr0.0003,retention0.02. Сохранять одинаковую исходную память/actor/value/log_std; обучать только conditional aim. Development используется для итогового отчёта, без выбора лучшего шага. Сравнение с прежним80-step BC не заменяет новую контрольную ветку: release разметка стала шире.

После CUDA проверок — свежий matched smoke:8 условий на вариант, контроль/vertical/правила,24 native/16 CUDA. Использовать существующий пул16 ×2 и свободные seeds с проверкой истории планов. На освобождённый слот подаётся следующий бой; второй пул параллельно не запускать. Успешная загрузка v2 и ненулевое использование ветки должны быть подтверждены трассой, а не только наличием полей в файле.

Если исходы и эффективность не ухудшены и есть положительный сигнал — screen24 условия/вариант. При отрицательном smoke остановить расширение оценки и изучить ошибки. Promotion исключён на обеих малых ступенях. Отдельно учитывать ordinary/recovery, урон, реальные native попадания и повороты/стояние/команды без цели. Дешёвое улучшение offline ошибки само по себе не основание увеличивать бюджет.

Полный PPO с новым контрактом потребует свежих own-policy боёв после BC и согласованного objective. Новую цель в bbox, снижение шума и JEPA-подобный auxiliary loss проверять последующими отдельными опытами, чтобы различать их эффект.

## Реализация и завершённое парное обучение

Версии `combat_sampled_motion_vertical_aim_v2` и `combat_sampled_motion_vertical_ablated_v2` имеют128→64→32→2,10402 параметра. Старый v1 сохраняет125→64→32→2,10210 параметров. В обеих новых версиях первые125 признаков прежние; различается только подача трёх категориальных каналов. Контроль подаёт нули, и новые столбцы после80 steps точно нулевые. Основной actor/critic/log_std и исходная временная память в обеих ветках сохранены.

Go `Decide` сохраняет yaw/pitch шумы в прежнем порядке RNG, после выбора vertical формирует окончательное среднее и однократно прибавляет сохранённый шум. `Review` и CUDA likelihood используют записанный vertical. Conditional retention точно суммирует три vertical категории по teacher probabilities вместе с target/mode. Нет подстановки будущего native состояния в рабочие признаки.

`scripts/migrate_combat_vertical_aim_cuda.py` создал два исходных update: `combat-vertical-aim-zero-v1-20261021` и `combat-vertical-aim-control-zero-v1-20261021`. На2213 реальных train histories обе миграции показали нулевую разницу raw outputs и эквивалентность средних для всех трёх vertical. Максимальное отклонение CUDA likelihood от исходного native0.000104. Проверены сохранение actor/value/std и Adam states, восстановление checkpoint, target=None, ненулевой vertical probe и точное KL по независимой аналитической формуле. Моменты новых входных столбцов, если они существуют, расширяются нулями.

Native compatibility `combat-vertical-aim-zero-native-evaluation-v3-20261021`:6 native/4 CUDA, две сцены старые/мигрированные/правила. На125 парных histories признаки и выбранные latent/attack/vertical/weapon/target/mode/seed совпали точно. Это проверка совместимости sampler, не оценка качества. Первые две подготовки остановились до native pool: унаследованные настройки обычного hypothesis stage не соответствовали диагностическому бюджету. Они сохранены как неисполненные подготовки; фактические бои прошли только в v3.

Парный протокол `combat-vertical-aim-ab-v1-20261021/protocol.json` закреплён до fit:80 steps,lr0.0003,retention0.02,seed20261022. Источники — две нулевые миграции одного zero-v1;1141 train/582 development пригодных метки после98/59 исключений. Остальные1239/641 метки сохранены в исходном экспорте. Исходные model SHA в histories не переписаны: trainer явно проверяет migration ancestry и точное соответствие нулевой миграции старой модели. Validation/coverage captures в fit не использовались.

CUDA pair audit подтвердил одинаковые начальные метрики, retention histories и неизменность остальных параметров. На641 фиксированной development истории диапазон поворота при смене только vertical: контроль0°, кандидат в среднем0.1647° по оси, максимум1.0479°. Это подтверждает использование выбранной команды, не оптимальность компенсации.

Promotion=false.
