# Сохранение и загрузка игрового состояния в харнесе

Первый срез от 01.10.2026: `cmd/q2checkpoint` и `internal/harness/checkpoint` управляют штатными `save`/`load` Yamagi через RCON. Это игровой savegame, а не телепорт или запись последней позиции бота. Сохранение содержит `server.ssv`, `game.ssv`, пары `.sav/.sv2` текущей и ранее посещённых карт. Версия формата1 пока поддерживает Windows runtime с `q2ded.exe` и `baseq2/game.dll`.

## Использование

Команда принимает только JSON-конфиг:

```powershell
go run ./cmd/q2checkpoint --config ./scripts/scenarios/checkpoint-save.example.json
go run ./cmd/q2checkpoint --config ./scripts/scenarios/checkpoint-load.example.json
```

Примеры требуют настройки под реально запущенный **изолированный** runtime. Сервер запускается с `-portable`, `+set ip 127.0.0.1`, `+set noipx 1`, `+set coop 1`, `+set deathmatch 0` и уникальным `+set sv_harness_instance INSTANCE`. В конфиге указываются его адрес, INSTANCE, runtime_root и checkpoint_dir; относительные пути разрешаются от файла конфига. RCON-пароль передаётся через `Q2COOPBOT_TEST_RCON`, в JSON и результаты не включается. Примеры не подключаются автоматически к человеческой игре. Воспроизводимый запуск с подготовкой runtime и двумя собственными серверами:

```powershell
./scripts/run_checkpoint_suite.ps1 -Port 30330
```

`save` требует нового checkpoint_dir и создаёт пакет `manifest.json` + `native/`. Манифест содержит карту из нативного server.ssv, UTC-время, размеры/SHA256 файлов сохранения, отпечатки серверного EXE/game.dll и PAK/BSP/AAS/ENT. Native слот каждый раз новый (`harness_...`); существующие пользовательские слоты не выбираются. Пакет считается готовым только после записи манифеста. Неполная запись не принимается для загрузки.

`load` проверяет целостность пакета, пары файлов карт и совпадение карты с server.ssv, точное совпадение runtime/ресурсов, идентичность изолированного сервера, baseq2 и отсутствие чужого writable home в нативных путях. Затем **копирует** файлы в новый локальный слот и запрашивает загрузку; общие сохранения не используют hard links. Исходный пакет не изменяется. Проверяется ответ штатной команды и карта после загрузки. Таймаут не приводит к повторной отправке операции с неизвестным исходом.

Результат `saved` подтверждает создание пакета; `load_acknowledged` — исполнение загрузки и карту. Поле `gameplay_verified=false` у инструмента остаётся явным: корректность позиции, здоровья, инвентаря, поколений и продолжения поведения должен подтвердить конкретный игровой сценарий. Нельзя засчитывать прохождение участка по одному ответу `load`.

## Проверено

`workspace/artifacts/checkpoint-suite-20261001-130124-435/report.json`:2/2 при2x, два независимых сервера/клиента одновременно, provenance_valid=true. Native размещение для теста получает Super Shotgun1/Shells10 и health38 на base2; сохраняется игра. Команда `map base1` намеренно заменяет её новой игрой: HP100, без Super Shotgun. После load возвращаются base2, исходные координаты `[304,-1888,-71.875]` с ошибкой0, HP38, Super Shotgun1/Shells10. Повторная загрузка той же base2 создаёт ещё одно новое поколение;6 свежих строк инвентаря подтверждают восстановление. Телепорт и `give health` исполнились только при исходной постановке, после загрузки повторно не применялись. Подбор при размещении является постановкой, а не доказательством навыка подбора.

Go-тесты проверяют полный пакет нескольких карт и копирование; отвергают изменённые ресурсы, повреждение, отсутствующий файл, symlink, перезапись пакета, чужой instance, подменённую карту, внешний адрес и произвольное действие. Путь с чужим home отвергается. `go test ./...` с BSP/AAS прошёл.

Ранний прогон130010 завершился1/2: проверка прочитала трассу до второго свежего кадра инвентаря. Проверка не ослаблена: теперь перед анализом явно ожидаются ещё5 игровых кадров того же поколения. Ранний125049 не проверял повторную загрузку той же карты и мог сохранять массив наблюдений из растущего JSONL; финальный reader выбирает одно последнее полностью прочитанное наблюдение.

## Следующие этапы

1. Синхронные точки сохранения/загрузки в JSON-сессиях: барьер клиентов, новая генерация после загрузки, сброс локальных счётчиков сценария и приёмка свежих наблюдений. Сейчас управление доступно отдельным инструментом и trial; действия save/load в Step/Phase ещё не добавлены.
2. Согласованный sidecar памяти/целей Go-бота и состояния исполнителя харнеса, с явным выбором: восстановление или чистый запуск. Нативное сохранение не содержит внешнюю память/состояние планировщика. Нельзя переносить знания из будущего участка в прошлый checkpoint молча.
3. Запуск новых процессов/новых runtime из общего checkpoint с отдельными копиями для параллельных ветвей. Текущая native приёмка проверяет загрузку в работающий сервер, а не восстановление после полного завершения процессов.
4. Проверка восстановленных дверей/лифтов/моста, врагов и ключей, затем сравнение политик и resource economy на одном checkpoint. Полное прохождение кампании пока не проверено.

Пакеты и native слоты находятся только в игнорируемом workspace; текущая человеческая игра не перезапускалась и её сохранения не изменялись.
