# Сохранение и загрузка игрового состояния в харнесе

Первый срез от 01.10.2026: `cmd/q2checkpoint` и `internal/harness/checkpoint` управляют штатными `save`/`load` Yamagi через RCON. Это игровой savegame, а не телепорт или запись последней позиции бота. Сохранение содержит `server.ssv`, `game.ssv`, пары `.sav/.sv2` текущей и ранее посещённых карт. Версия формата1 пока поддерживает Windows runtime с `q2ded.exe` и `baseq2/game.dll`.

## Использование

Команда принимает только JSON-конфиг:

```powershell
go run ./cmd/q2checkpoint --config ./scripts/scenarios/checkpoint-save.example.json
go run ./cmd/q2checkpoint --config ./scripts/scenarios/checkpoint-load.example.json
```

Примеры требуют настройки под реально запущенный **изолированный** runtime. Сервер запускается с `-portable`, `+set ip 127.0.0.1`, `+set noipx 1`, `+set coop 1`, `+set deathmatch 0` и уникальным `+set sv_harness_instance INSTANCE`. В конфиге указываются его адрес, INSTANCE, runtime_root и checkpoint_dir; относительные пути разрешаются от файла конфига. RCON-пароль передаётся через `Q2COOPBOT_TEST_RCON`, в JSON и результаты не включается. Примеры не подключаются автоматически к человеческой игре. Воспроизводимый запуск с подготовкой runtime и двумя собственными серверами:

```powershell
./scripts/run_checkpoint_suite.ps1 -Port 30330
```

`save` требует нового checkpoint_dir и создаёт пакет `manifest.json` + `native/`. Манифест содержит карту из нативного server.ssv, UTC-время, размеры/SHA256 файлов сохранения, отпечатки серверного EXE/game.dll и PAK/BSP/AAS/ENT. Native слот каждый раз новый (`harness_...`); существующие пользовательские слоты не выбираются. Пакет считается готовым только после записи манифеста. Неполная запись не принимается для загрузки.

`load` проверяет целостность пакета, пары файлов карт и совпадение карты с server.ssv, точное совпадение runtime/ресурсов, идентичность изолированного сервера, baseq2 и отсутствие чужого writable home в нативных путях. Затем **копирует** файлы в новый локальный слот и запрашивает загрузку; общие сохранения не используют hard links. Исходный пакет не изменяется. Проверяется ответ штатной команды и карта после загрузки. Таймаут не приводит к повторной отправке операции с неизвестным исходом.

Результат `saved` подтверждает создание пакета; `load_acknowledged` — исполнение загрузки и карту. Поле `gameplay_verified=false` у инструмента остаётся явным: корректность позиции, здоровья, инвентаря, поколений и продолжения поведения должен подтвердить конкретный игровой сценарий. Нельзя засчитывать прохождение участка по одному ответу `load`.

### 01.10.2026 — portable state API для памяти и исполнителя

Начат следующий пункт после limited grenade MVP. PlannerCheckpoint сохраняет цель/точку цели, death/rendezvous и память аптечек/брони с относительным возрастом и признаком уже неудачной попытки. RestoreCheckpoint работает с новым Planner и первым свежим native snapshot после load, загружает геометрию карты, пересчитывает возраст под новый network frame; знания о текущей видимости, HP/инвентарь и motor actions не восстанавливаются. Даже ранее observed ресурс становится unknown; unavailable и attempted сохраняются. Захват на смерти, в воздухе, при прыжке/лифте, подготовке ручной гранаты или видимом projectile отвергается.

RunnerCheckpoint поддерживает активные обратимые wait/walk шаги: SHA256 определения сценария, StepID/index и elapsed frames. При восстановлении в новой генерации остаток бюджета сохраняется, entry action не повторяется. Изменённый сценарий и некорректный прогресс отвергаются; kill/respawn/place/shoot steps пока не поддержаны. Две ветви получают независимые копии.

Go-тесты проверяют JSON roundtrip памяти, age rebase даже при новом frame2, unavailable/attempted, отсутствие будущих наблюдений, независимость ветвей, wrong-map/negative-age rejection и запрет armed capture. Для runner проверены тот же остаток20-frame wait, отсутствие повторного NewStep/Kill/Place, новый generation и отказ при изменении сценария.

Это API полезной нагрузки будущего sidecar, а не подключённая функция save/load JSON-сессий. Согласованный барьер bot+actor+native, упаковка с манифестом, выбор resume/fresh и native восстановление новых процессов ещё не реализованы. Они остаются следующим пунктом; не засчитывать существующий native-only checkpoint как приёмку этих API.

Дополнительная приёмка: все9 отрицательных контролей автоматических гранат отвергнуты (missing start/release/consumption, held ATTACK, урон напарнику, forced arming; потерянный инвентарь/unsafe selection/projectile в отказном случае). Файл workspace/artifacts/grenade-auto-suite-20261001-191110-623/negative-controls.json. Native-only checkpoint regression: workspace/artifacts/checkpoint-suite-20261001-191226-512/report.json,2/2 на2x/parallelism2,provenance true. Эта регрессия проверяет сохранение native позиции/HP/инвентаря и новую генерацию, не совместное восстановление новых PlannerCheckpoint/RunnerCheckpoint.

### 01.10.2026 — согласованный capture/save барьер

Сохранение теперь может включать native состояние сервера и sidecar памяти двух Go-клиентов, а для сценарного актёра — ещё и прогресс RunnerCheckpoint. Контроллер выбирает будущий frame и generation; изолированный Yamagi останавливает мир и network frame вместе, продолжая обслуживать RCON/netchannel. В этот момент движения и игровые client commands блокируются. Обычный pause для coop не использован: он не обеспечивает такую остановку. Режим активен только при заданном sv_harness_instance и положительном sv_test_checkpoint_frame.

Клиенты с test.checkpoint_control и frame_paced отвечают атомарным JSON только после обработки выбранного кадра. Проверяются карта, поколение, frame планировщика/исполнителя, допустимость захвата и уникальность участника. После ответов всех клиентов сервер подтверждает тот же якорь, выполняется native save, повторно проверяется якорь, записываются sidecar и размеры/SHA256 в manifest.json; затем барьер снимается. При ошибке контроллер тоже пытается снять его. Загрузка проверяет контрольные суммы sidecar, имена/уникальность участников и согласованность внутренних кадров до изменения сервера. Пустой корректный RCON print считается ответом: успешный set обычно не содержит текста.

Следующий пункт — согласованное восстановление с выбором resume/fresh и новые процессы. ### 01.10.2026 — Go resume/fresh после native load

Подключено восстановление PlannerCheckpoint/RunnerCheckpoint в новых клиентах. В test задаются checkpoint_restore (путь к пакету), checkpoint_mode (обязательно resume или fresh) и checkpoint_control (путь для подтверждения). ReadParticipant проверяет manifest/весь набор sidecar, контрольные суммы и привязку native слотов, затем выбирает участника по имени. Native загрузку и соответствие runtime по-прежнему проверяет отдельный контроллер. Клиент применяет состояние до первого planner.update/игровой команды, после свежего живого grounded snapshot нужной карты, своего слота и нового поколения. До этого отправляются только сетевые подтверждения.

resume переносит цель, death/rendezvous и память ресурсов с пересчётом возраста относительно нового кадра. Текущие HP/инвентарь/видимые объекты остаются native наблюдением, маршруты и motor actions не восстанавливаются. Для сценарного актёра определение должно совпасть по digest, активный wait/walk продолжается с сохранённым elapsed без повторного entry/placement. Наличие runner в sidecar и конфиге должно совпадать. fresh отбрасывает сохранённую память/прогресс; конфиг с активным scenario при fresh пока отвергается, чтобы не переиграть первоначальный teleport. Для чистой политики scenario не указывают. Restore несовместим с initial teleport/give health, invulnerability, JSON session и отдельной travel memory.

Подтверждение пишется атомарно в checkpoint_control.restored.json: режим, участник, исходный/новый кадр, поколение/слот, память непосредственно после применения и исходный elapsed runner. Состояние публикуется до первой новой команды, поэтому дальнейшее решение политики может изменить цель без подмены подтверждения. Ошибка проверки не начинает частичное выполнение сценария.

Wrong slot/old generation/неизвестный режим/изменённый сценарий отвергаются до применения. ### 01.10.2026 — две ветви одного checkpoint и метрики
