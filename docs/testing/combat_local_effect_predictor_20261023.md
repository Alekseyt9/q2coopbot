# Прогноз ближайшего урона: первая обученная пара не допущена к управлению

23 октября 2026. Завершены два фиксированных GPU обучения по `../combat_local_effect_predictor_protocol_20261023.json`. Прогноз нанесённого урона улучшился относительно постоянного среднего, но прогноз полученного урона и последствий альтернативных действий не прошёл допуск. Боевой actor/critic/std, рабочие веса и default не менялись. Новых игр в этом опыте нет.

Seed/map/fork seed используются только для группировки и не входят в NN.

Вход1185:1147pre-command features, фактические source/final latent действия, attack, one-hot target/aim-mode/vertical/weapon и объявленная остающаяся поправка движения. Будущие наблюдения и native damage — только targets. Отсутствующий aim-candidate event означает неизменный source=final latent, как в основном CUDA likelihood verifier. Native sample используется для полного event, а CUDA row — для проверенных features.

Для горизонтов1/3/5/10суммируются только известные эффекты точных exclusive native окон. Реальная цель либо смерть останавливает target на подтверждённом terminal окне; это объявленная остановка задачи, а не приписывание нулевого урона неизвестному физическому будущему. Nonterminal handoff и missing trace остаются masked. Во всех отобранных переходах эти горизонты известны; например, TRAIN H10включает626наблюдений, остановленных по goal, и170по death. Хранение — сжатые NPZ chunks, всего3631688байт (около3,46МиБ), плюс небольшая JSON provenance. Исходные записи не менялись. Первый metadata build остановился до записи chunks из-за отсутствующего optional aim-candidate event; исправлен выбор полного native sample и fallback без коррекции, успешный отдельный build сохранён какv2.

## Два фиксированных GPU fit

Одинаковая MLP1185→64→32→24,78776параметров. На каждом из4горизонтов — четыре event logits и два ожидаемых значения полученного/нанесённого урона. Loss — BCE плюс squared error amounts/20, только known targets. State-only использует те же1185входов, но весь блок действия занулён. Совпадают начальные параметры, последовательность sampled batches, AdamW и800шагов; endpoint только последний, без checkpoint search. Оба fit, метрики, counterfactual сравнения и reload proof выполнены наCUDA.

Начальная выходная голова задаёт TRAIN константу; скрытая часть одинакова у обоих вариантов. Это не изменение исходной боевой сети. Checkpoint содержит состояния предиктора/optimizer; повторная загрузка наGPU дала те же development outputs.

НаTRAIN полученный RMSE4,2018иBCE0,3564, заметно лучше development: текущий fit переносится плохо. Из этого не следует, что более крупная сеть исправит проблему либо что действия бесполезны.

## Дополнительный CUDA разбор области обучения

Отдельный post-hoc audit без fitting обнаружил важное ограничение: в TRAIN remaining window принимает только0/1, а challenge содержит ещё5. Поэтому отрицательный long-action прогноз частично относится к отсутствующей в обучении длительности, а не доказывает невозможность предсказывать её после подходящего сбора. Исходный отказ сохранён.

Однако и short-only H10не проходит: received delta RMSE10,4192против10,2918нулевого эффекта (×1,012), dealt7,5283против6,2048 (×1,213). Поэтому отсутствие длительности5не объясняет весь отказ. НаH1observed action delta этих корневых состояний нулевая; модель выдумывает небольшую разницу. Это аргумент в пользу отдельного обучения причинным эффектам/геометрии, а не использования хорошей общей damage regression как готового оценщика манёвров.

## Следующий шаг

Не дообучать эти endpoints по просмотренным challenge outcomes и не внедрять их в runtime. Следующий небольшой опыт должен проверить shared per-enemy модель угрозы с наблюдаемыми типом, animation frame, относительной позицией/скоростью/направлением и собственным фактическим движением. По native event можно дать отдельную метку урона от каждого наблюдаемого противника, сохранив неизвестных атакующих отдельной категорией. Это сокращает смешивание причин урона разных мобов и зависимость от абсолютной геометрии карты; предполагаемая польза ещё не проверена.

Для новых контрфактических примеров выбирать TRAIN моменты по уже наблюдаемому обстрелу/снижению здоровья и видимым противникам, а не по исходу будущей альтернативы. Старые root состояния почти не дают различий receiveddamage наH1..5. Нужны явные in-support action durations; нельзя проверять learned duration5там, где обучение видело только1. После predictive/counterfactual допуска всё ещё нужны новые физические условия, сравнение с source/rules и campaign/coop проверка.
