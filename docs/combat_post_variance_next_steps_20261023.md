# Следующий опыт после проверки случайности продолжений

23 октября 2026. Цель прежняя: полный обучаемый бой должен устойчиво превосходить правила. Сейчас такого результата нет. Не продолжать отклонённые500-step selectors и не менять их development пороги.

## Что изменило следующий шаг

Из19проверенных предпочтений однокадрового движения15меняют знак при смене дальнейшей случайности политики. Один исход оказался слабой меткой «лучшего действия». При этом frozen motor действительно прогнозирует изменение позиции. Это конкретная проблема текущего парного supervised подхода, но не доказательство единственной причины всех прежних PPO неудач.

Перед большим сбором усреднённых меток проверить более дешёвую гипотезу: не слишком ли велик непрерывный шум выполнения уже обученной политики. Это отдельная калибровка распределения действий, не новое обучение и не перевод на правила. Случайность категориальных выборов этим опытом не устраняется.

## 1. Две проверенные policy forks на GPU

Источник: `workspace/artifacts/combat-geometry-nonterminal-objective-v3-20261023/initializer`, SHA весов `559ff0ad4297047cdc4a9ad531fa9159668b045b7f41bf8e32a6df975278bea6`.

- `movement-quarter`: умножить Gaussian std первых двух latent координат движения на0,25; aim std прежние.
- `all-quarter`: умножить std всех четырёх непрерывных координат на0,25.

Изменять только `log_std`. Actor/critic/attention/условный прицел/fire/оружие/geometry head/predictors остаются прежними. Изменения conditional outputs при **новом sampled movement** ожидаемы; нельзя объявлять их неизменными по одному совпадению raw actor.

Существующий `fork_combat_aim_noise_cuda.py` — полезный образец, но он меняет только aim и предполагает старую структуру checkpoint. Не запускать его вслепую на Geometry8. Новый helper должен явно восстановить текущие actor optimizer groups, сбросить только моменты Adam изменённых std координат, сохранить остальные параметры/моменты/шаги, critic/geometry optimizer, RNG и consumed history. Обновить checkpoint log_std/weights SHA; проверить сохранение и чтение наCUDA. Не выдавать несовместимую копию старого checkpoint за новый resumable fork и не снимать retention ограничения молча.

На закрытых TRAIN историях CUDA проверяет совпадение неизменённых NN tensors, raw actor/value и условных модулей при фиксированных действиях; ожидаемое изменение std; допустимые границы[-8,1]; соответствие JSON/checkpoint/optimizer. У текущего источника четверть std укладывается в границы без clipping. Исходные файлы не менять. Истории здесь только для технической проверки, не для fitting.

## 2. Фиксированный малый native screen

Реестр: `workspace/artifacts/combat-geometry-nonterminal-objective-v3-20261023/comparison-registry/index.json`.

Четыре варианта: source, movement-quarter, all-quarter, rules. По одному **новому validation seed** каждого из восьми ordinary/recovery семейств четырёх карт. Выбрать следующий неиспользованный offset по истории планов и зафиксировать spec до игр.32native/24CUDA, существующий динамический пул16, ×2. Все варианты получают одинаковые generated fixtures. Не включать прежние состояния/повторы RNG в качество этого screen.

Это обычные стохастические Gaussian policies с положительным std, поэтому специальный deterministic/inference-only runtime или подмена q не нужны. Использовать существующую полную CUDA проверку likelihood/value/memory/transform и geometry logits; sourceNN вGo только в реальных играх. Новые diagnostic continuation headers здесь запрещены.

## 3. Решение до получения исходов

Для допуска лишь к независимому подтверждению кандидат должен выполнить все условия:

- целей не меньше `min(8, source_goals+2)` и `min(8, rules_goals+1)`;
- смертей не больше source и rules;
- полученный урон не больше1,1отrules;
- доля фактических MG выстрелов с уроном живому монстру не ниже source минус3процентных пункта;
- доля крупных поворотов≥30° не выше source плюс2п.п., атаки без выбранной цели не выше source плюс3п.п.

Правило потолка8задано заранее. Если пройдут оба — больше целей, затем меньше смертей, затем меньше полученного урона, затем имя варианта. Не менять пороги, не выбирать промежуточный checkpoint и не повторять неудачные сиды.

При успехе ещё нужна новая24-case-per-variant confirmation как минимум против source и rules, затем campaign/coop acceptance. Малый screen не разрешает production promotion. Если оба не пройдут, их не дообучать/не гонять дальше без нового обоснования.

## 4. Затем исправлять учебные метки

Следующий обучающий набор должен иметь несколько общих случайных продолжений на каждую пару «состояние/манёвр», а не назначать победителя по единственному исходу. Принятый continuation-fork контракт уже позволяет такой сбор. Нужны новые целые TRAIN/development сиды и геометрии; нынешние четыре development состояния использованы исследовательски и не годятся для нового независимого подтверждения.

Сначала определить достаточное число продолжений (например4против8) по разбросу парной utility и устойчивости среднего, затем фиксировать бюджет большого сбора. Не считать среднее нескольких наблюдений точнымQ. Если различия средних остаются малы относительно разброса, отдельным протоколом проверить более длительные манёвры/осмысленные action chunks вместо бесконечного увеличения сети.

## 5. Сохранить скорость проверки гипотез

Не запускать большой fitting до приёмки данных и не тратить quality бои на не прошедшие offline endpoints. Повторно использовать закрытые захваты и кэшировать frozen forecasts, не копировать PAK/AAS, сохранять один native pool до16. Проверять фактическое завершение цели; пустой хвост остановки не должен превращаться в учебные действия. Все неудачные gates и технические отказы остаются в журнале.
